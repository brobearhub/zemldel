# SEO-аудит zemledel.ru — 5 ноября 2026

Проверены опубликованный сайт и текущий код frontend. Обойдены все 23 страницы категорий, главная, `/about`, четыре документа, опубликованная услуга и профиль исполнителя, страницы входа и восстановления пароля, `/themes`, тестовые несуществующие URL. Проверены robots.txt, sitemap.xml, HTTP → HTTPS, www и Open Graph. Главная проверена в отдельном Chromium на ширине 1440 и 390 px, страница услуги и отсутствующего пользователя — на 390 px. Формы не отправлялись.

Проверка выявила технические ошибки и недостаток наполнения: опубликована одна услуга, 21 из 23 страниц категорий показывают отсутствие услуг. Это ограничивает количество полезных посадочных страниц для поиска.

Данные Google Search Console, Яндекс Вебмастера, органический трафик и полевые Core Web Vitals не были доступны. Нельзя по этому аудиту утверждать, какие URL уже находятся в индексе, какие санкции применены или какая именно ошибка вызвала потерю позиций. Приведённые ниже наблюдения относятся к сайту и коду, а не к состоянию поискового индекса.

## 1. Каталог главной: SSR и стабильность загрузки

В `frontend/app/(site)/page.tsx` на сервере загружаются категории. Компонент `frontend/widgets/services/ui/HomeServicesByCity.tsx` начинает с `null` и запрашивает услуги в `useEffect`. Поэтому исходный HTML главной содержит навигацию и форму, но не карточки услуг. Категории и sitemap позволяют обнаружить услугу другими путями; полной недоступности услуги для роботов не обнаружено.

Google умеет выполнять JavaScript, но каталог зависит от дополнительной загрузки и рендеринга. Надёжнее отдавать начальные карточки и ссылки на сервере. Это соответствует [рекомендациям Google по JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics).

Мобильная проверка 390 × 844 без искусственного замедления сети/CPU:

| Запуск | LCP | Сдвиг при загрузке |
| --- | --- | --- |
| Первый, новый контекст | 2,556 с | 0,171 |
| Повтор в новом контексте | 2,724 с | 0,164 |
| Повтор с тёплым кешем | 1,224 с | 0,164 |

В двух дополнительных запусках LayoutShift API зафиксировал один основной сдвиг: футер из видимой области с y=551 переместился за экран при появлении каталога. Это согласуется с отсутствием карточки и зарезервированного места в начальном HTML.

Это лабораторные наблюдения загрузки, не Lighthouse score и не полевые Core Web Vitals. INP не измерялся. Для CLS целевой хороший уровень — не более 0,1, оцениваемый по 75-му перцентилю посещений: [web.dev](https://web.dev/articles/cls).

Критерий исправления: карточки и ссылки присутствуют в исходном HTML; выбор города работает; повторная мобильная проверка не воспроизводит этот скачок.

## 2. Sitemap: актуальность и состав

`frontend/app/sitemap.ts` не задаёт `revalidate` или динамический режим. Данные запрашиваются через Axios, а не через Next.js fetch. В существующей локальной сборке `/sitemap.xml` имеет `initialRevalidateSeconds: false`. В коде не найдено вызовов `revalidatePath`/`revalidateTag`. Next.js [кеширует sitemap по умолчанию](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/sitemap).

Опубликованный sitemap отдаёт `x-nextjs-cache: HIT`. Сам по себе HIT не доказывает устаревание. Текущая опубликованная услуга присутствует в sitemap; добавление новой услуги для проверки обновления не выполнялось. Риск отсутствия обновлений подтверждён конфигурацией и локальным build manifest.

Независимая подтверждённая проблема: фильтр `category.parentId == null` исключает все подкатегории. Рабочая страница `/service-categories/462a2598-e83e-4580-bcd9-1f46d47aef3e` («Подключение электричества») содержит услугу, отвечает 200 и связана навигацией, но отсутствует в sitemap.

Также ошибки API перехватываются с заменой данных на пустые массивы. При недоступном backend во время генерации может сохраниться неполный sitemap с успешным статусом.

Критерий исправления: новые опубликованные услуги появляются в пределах согласованного срока, снятые с публикации исчезают; сбой backend не заменяет корректную карту на пустую; содержательные подкатегории включены, URL с noindex исключены.

## 3. Наполнение и поисковые намерения

Публичный `/api/services` вернул одну опубликованную услугу. Содержание есть у одной подкатегории и её родительской категории; остальные 21 категория не имеют услуг. Одного названия категории и одинаковой формы заявки мало для убедительной посадочной страницы по запросам вроде «межевание участка» или «исправление кадастровой ошибки».

Для реально оказываемых услуг нужны конкретные сведения: что входит, где выполняются работы, результат, этапы, сроки, документы от клиента, условия расчёта цены, реальные исполнители и подтверждённые примеры. Не следует выдумывать цены, кейсы, гарантии или географию. Пустые категории можно оставить для навигации и временно исключить из индекса, либо наполнить самостоятельным полезным материалом. Сам факт отсутствия карточек не требует автоматически закрывать качественную информационную страницу.

Главная сейчас использует общий брендовый title. Возможное направление: «Земельные и кадастровые услуги — Земледел». Регион следует добавлять только согласно реальной географии площадки. Массовую генерацию одинаковых городских страниц до появления полезного локального содержания не планировать.

## 4. Метаданные и заголовки

На главной, `/about`, всех категориях и документах отсутствует canonical. Вариант главной `/?utm_source=seo-audit` возвращает ту же страницу без canonical. У действующей услуги и профиля исполнителя canonical уже есть и совпадает с их URL.

Добавлять canonical следует отдельно для каждой публичной страницы, а не наследовать главную как canonical для всего сайта. Рекомендации: [Google о canonical](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls).

В `frontend/widgets/service-page/ui/ServiceHeroSection.tsx:133` название услуги выводится через `Typography variant="h4"` без `component="h1"`. После браузерного рендеринга H1–H3 на странице услуги отсутствуют. Внешний размер заголовка можно сохранить, изменив семантический тег.

Четыре страницы документов не экспортируют metadata, а в корневом layout нет запасного title. Их HTML действительно приходит без `<title>`. Исправление текста юридических документов для этого не требуется.

## 5. Статусы и служебные страницы

Несуществующая общая страница, несуществующая услуга и несуществующий исполнитель корректно возвращают 404 с noindex. Но `/users/[id]` загружает данные на клиенте и возвращает страницу «Профиль скрыт» со статусом 200. Такое поведение создаёт риск soft 404; фактическую классификацию Google нужно проверить в Search Console. [Определение soft 404 у Google](https://developers.google.com/search/docs/crawling-indexing/troubleshoot-crawling-errors).

Дополнительный риск в коде: `getPublicProviderBySlug()` в `frontend/entities/provider/api/provider.server.ts` превращает любую ошибку backend в `null`. Страница `/providers/[slug]` затем вызывает `notFound()`. Поэтому временная недоступность API может выглядеть как исчезновение существующего профиля. На production сбой не имитировался. Следует различать настоящий 404 и 5xx/сетевую ошибку.

Для `/themes`, входа, регистрации и восстановления пароля не найдено noindex ни в метаданных ответа, ни в HTTP-заголовках. Они доступны поисковым роботам; это не доказывает, что они уже проиндексированы. Для исключения из индекса применять noindex. Блокирование в robots.txt не позволяет роботу прочитать noindex: [Google о блокировке индексации](https://developers.google.com/search/docs/crawling-indexing/block-indexing).

## 6. Домен и превью

`http://zemledel.ru/` правильно перенаправляется 308 на `https://zemledel.ru/`. HTTPS основного домена проверен curl и Chromium без отключения проверки сертификата.

`https://www.zemledel.ru/` завершает TLS handshake ошибкой. `http://www.zemledel.ru/` перенаправляется 308 на этот же неработающий HTTPS www. Требуется проверить доменный алиас и сертификат у хостинга, затем редирект www → основной домен. Причина на уровне конкретной настройки хостинга не установлена; изменения DNS и сертификатов не выполнялись.

Главная ссылается на `https://zemledel.ru/og-image.png` в Open Graph и Twitter metadata. URL возвращает 404. Это подтверждённая ошибка превью ссылки, но не главный фактор поисковой индексации.

## Локальные исправления после аудита

Изменения подготовлены в рабочем дереве; на опубликованном сайте они ещё не проверены и не развёрнуты.

- Главная получает каталог на сервере. Карточки доступны в исходном HTML; выбор города остаётся интерактивным. Сохранённый город восстанавливается после гидратации, чтобы первый клиентский HTML совпадал с серверным.
- Существующие 23 страницы категорий превращены в содержательные разделы: 6 корневых хабов и 17 подкатегорий. Для каждой написаны отдельные введение, два тематических блока, список исходных материалов и ответ на вопрос. На корневых страницах есть ссылки с пояснениями на подкатегории; на дочерних — ссылка на родителя. Нет вымышленных цен, сроков, выполненных проектов или обещаний результата.
- Адреса с UUID сохранены. Если API принимает slug той же категории, страница перенаправляет его на основной адрес. Добавлены canonical и BreadcrumbList. Для мобильной версии предусмотрен переход к форме по якорю.
- Sitemap строится по актуальному публичному каталогу при запросе и включает подкатегории. Ошибка зависимости больше не подменяется успешной неполной картой.
- Добавлены title, description и canonical публичных страниц; исправлена ссылка на существующее изображение Open Graph/Twitter. Название услуги стало H1.
- Страницы входа, регистрации, восстановления пароля, личного кабинета, чатов и демонстрации тем получили noindex. Общие профили пользователей также закрыты от индексации.
- Недоступные публичные профили пользователей проверяются на сервере и вызывают notFound. Авторизованный доступ владельцев и участников договора сохранён. Ошибки backend у профилей исполнителей больше не превращаются в ложный 404.
- В приложении добавлен постоянный редирект www → основной домен. Он не исправляет TLS: сертификат и подключение www по-прежнему требуют проверки на стороне хостинга.

### Как поддерживать тексты

Редакционные материалы находятся в `frontend/entities/service-category/model/category-guides.ts`, привязка идёт по стабильному slug категории. Отображение — в `frontend/widgets/service-categories/ui/CategoryGuideSection.tsx`. При добавлении новой категории подготовьте отдельный материал и расширьте тест покрытия категорий. Если категория пока не имеет предложений, страница прямо сообщает об этом; текст не выдаёт отсутствующие предложения за доступные услуги.

Уточняйте цены, географию, сроки и состав предложения только по данным исполнителей. При изменении правовых процедур перепроверяйте соответствующий текст. Справочный материал помогает сформулировать задачу и не подменяет анализ документов конкретного объекта.
