# Приватное хранение документов

Все файлы, загружаемые как документы заявки клиентом или исполнителем, направляются в один приватный бакет с обязательным SSE-KMS. Это договоры, приложения, откреплённые подписи, документы по запросам исполнителя и файлы/фотографии этапов работ. Аватары, обложки и изображения публичных историй остаются публичным контентом.

## Реализация

`DocumentStorageService` используется сервисами `ContractFilesService`, `RequestDocumentRequestsService` и `RequestWorkStagesService`.

- Новые ключи начинаются с `documents/`. Они содержат технические идентификаторы и расширение, без исходного имени файла и паспортных реквизитов.
- Общий метод записи всегда передаёт `ServerSideEncryption: aws:kms`, ID выделенного KMS-ключа и `CacheControl: private, no-store`. Неудачная запись не переключается на старый бакет.
- Файлы скачиваются через backend после существующих проверок пользователя, исполнителя, заявки и стадии её исполнения. Публичные ссылки и CDN для документов не выдаются.
- При удалении перечисляются и удаляются все версии точного ключа, включая `null` и delete markers, затем проверяется отсутствие оставшихся копий. Это действует также для старого S3 при очистке. У runtime-аккаунта старого хранилища должны быть права ListObjectVersions/DeleteObjectVersion.
- Удаление файла/этапа не стирает ссылки в БД при ошибке очистки хранилища, чтобы операцию можно было повторить. Частичное удаление нескольких файлов может потребовать повторного запроса.
- Старые пути читаются из прежнего приватного бакета до миграции. Для исторических договоров сохранён локальный fallback. Для новых ключей fallback отсутствует.

Общий защищённый клиент пока называется `PassportStorageService`, а параметры подключения — `PASSPORT_S3_*`: имена сохранены после расширения назначения бакета. Все шесть переменных перечислены в `backend/.env.example`. Ключ runtime отличается от ключа Terraform. Секреты остаются только в закрытом файле вне репозитория и локальном игнорируемом `backend/.env`; для сервера их нужно добавить в секреты окружения backend.

Новые анкеты паспорта сохраняются отдельными JSON-объектами `passports/<user-uuid>/form/<random-uuid>.json` с SSE-KMS. `PassportDocument` содержит ссылку и SHA-256, прежние поля с шифротекстом при сохранении очищаются. Исторические анкеты в БД читаются через `DocumentsCryptoService` и переходят в S3 при следующем сохранении; до этого прежний мастер-ключ нужен для чтения.

Фотографии паспорта сохраняются как изображения в `passports/<user-uuid>/photos/<random-uuid>.<ext>` с SSE-KMS. Разрешены четыре изображения JPEG, PNG или WebP до 10 МиБ каждое и до 40 миллионов пикселей. Backend проверяет сигнатуру и декодирует изображение через Sharp, исправляет ориентацию и удаляет метаданные при повторном кодировании. Исходное имя не сохраняется; в `PassportPhoto` остаются ссылка, SHA-256, MIME, размер и служебные идентификаторы. Повтор загрузки использует тот же `uploadId`; сервер проверяет совпадение содержимого и не создаёт дубликат. Ограничение количества проверяется также внутри блокировки пользователя, включая параллельные запросы.

Backend-маршруты `documents/passport/photos/mine` и `documents/passport/photos/mine/:id` доступны только владельцу. BFF проксирует их через `/api/documents/passport/photos` и `/api/documents/passport/photos/:id`; изображения отдаются без публичных ссылок, с `private, no-store` и `nosniff`. Интерфейс загружает сохранённый список, открывает фотографию и удаляет её после подтверждения. При сбое можно повторить загрузку или удаление. Кнопка «Поделиться» позволяет выдать раздельные разрешения на анкету и фотографии по заявке.

Операции над анкетой одного пользователя сериализованы блокировкой PostgreSQL. До PUT регистрируется задача очистки незавершённой загрузки с задержкой один час — дольше сетевых таймаутов. Если PUT или фиксация БД прервутся, объект останется учтённым для последующей очистки. Успешное сохранение удаляет эту задачу вместе с обновлением ссылки в одной транзакции.

Триггеры БД регистрируют очистку предыдущего объекта при замене/удалении анкеты или фотографии, в том числе при каскадном удалении пользователя. Очередь `PassportObjectCleanup` не имеет FK к пользователю, чтобы задача пережила удаление аккаунта. Backend пытается удалить прежние объекты сразу и повторяет неудачные операции каждую минуту. Очистка проверяет, что ключ не является текущей анкетой или сохранённой фотографией, и удаляет все его версии/markers. Ошибка явного удаления не выдаётся за успешную очистку; задача остаётся для повтора. При недоступном backend фоновые повторы возобновятся после его запуска.

Для ответов анкеты на backend и BFF установлено `Cache-Control: private, no-store`. Автоматический доступ исполнителя по статусу заявки удалён; чтение требует действующего явного разрешения соответствующего вида.

## Разрешения на паспорт

`PassportAccessGrant` хранит независимые разрешения `FORM` / `PHOTO` с привязкой к владельцу паспорта, заявке, выбранному исполнителю и сроку. Клиент выбирает 1, 7 или 30 дней. Это доступ исполнителя как организации/профиля: читать могут его активные сотрудники с правом чтения заявок. Администратор платформы не получает доступ через этот API.

- Без разрешения анкета и фотографии не читаются, в том числе по активной заявке. Нельзя выдать доступ по чужой заявке, без выбранного исполнителя или по завершённой/отменённой/закрытой заявке.
- Разрешение охватывает текущие данные выбранного вида и их изменения до истечения срока; это указано в диалоге. Снятие галочки отзывает соответствующий вид доступа по этой заявке.
- Каждое чтение проверяет пользователя, исполнителя, заявку, вид и срок. Общая блокировка владельца сериализует чтение с отзывом и удалением; после фиксации отзыва новый запрос чтения не проходит. Уже полученные копии отозвать нельзя.
- Изменение исполнителя/клиента или переход заявки в `COMPLETED`, `CANCELLED`, `CLOSED` удаляет разрешения триггером БД. Повторное открытие заявки не восстанавливает согласие.
- Удаление анкеты через API отзывает `FORM`. Удаление последнего фото отзывает `PHOTO`; удаление одного из нескольких снимков сохраняет разрешение на оставшиеся.
- Выдача, отзыв, автоматическое закрытие доступа и успешное чтение содержимого записываются в `PassportAccessAudit` без паспортных реквизитов. Клиент видит последние 50 событий.

Маршруты клиента: `GET /documents/passport/access`, `PUT /documents/passport/access/:requestId` с `{form, photo, durationDays}`, `DELETE /documents/passport/access/:requestId/:kind`. Маршруты исполнителя: прежний `GET /pro/requests/:id/passport`, новый список `GET /pro/requests/:id/passport/photos` и чтение `GET /pro/requests/:id/passport/photos/:photoId`. BFF проксирует эти маршруты с префиксом `/api`. Все ответы с содержимым используют `private, no-store`, фотографии — также `nosniff`. Публичные или подписанные S3-ссылки не выдаются.

Исполнитель может отдельно запросить данные паспорта (`FORM`) и фотографии (`PHOTO`): `POST /pro/requests/:requestId/passport/access-requests/:kind`. `GET` без `:kind` возвращает `pendingKinds`. Запрос доступен только действующему исполнителю текущей заявки, не открывает паспорт и не требует, чтобы клиент уже заполнил данные. Повторный запрос того же вида идемпотентен. Ожидающие запросы хранятся в `PassportAccessRequest` (миграция `20261112210000_passport_access_requests`), события запроса и отклонения — в существующем журнале.

Клиент видит запросы под «Доступ исполнителей к паспорту» и может выдать доступ через существующее окно с заранее выбранной заявкой или отклонить запрос: `DELETE /documents/passport/access/requests/:requestId/:kind`. `GET /documents/passport/access/requests` возвращает только ожидающие запросы владельца без паспортных реквизитов. Выдача разрешения убирает запрос только соответствующего вида; смена клиента/исполнителя или закрытие заявки удаляет ожидающие запросы без их восстановления при повторном открытии. Уведомления используют существующее событие `request.changed`; клиент обновляется также при возвращении во вкладку и раз в минуту в видимой вкладке. До решения у «Документов» видна красная точка без счётчика, текст и кружок у колокольчика используют общую анимацию `shared/ui/attention-gradient.ts` с поддержкой `prefers-reduced-motion`.

При сохранении разрешений интерфейс также передаёт выбранный `providerId`: сервер сверяет получателя с текущим исполнителем заявки и отклоняет устаревшее подтверждение после переназначения.

Миграция `20261106180000_passport_access_grants` применена локально. Старый автоматический доступ не преобразуется в разрешения: клиент должен выдать их явно. На сервере миграция и приложение ещё не развёрнуты.

## Развёртывание и перенос

1. Применить миграции `20261106120000_passport_object_storage`, `20261106130000_passport_photos` и `20261106180000_passport_access_grants` перед развёртыванием backend; они добавляют ссылки, таблицу фотографий, очередь и триггеры очистки. Локально эти миграции уже применены, на сервере — ещё нет. Добавить `PASSPORT_S3_*` в секреты окружения backend и развернуть код, поддерживающий оба вида ключей. Без этих параметров новые загрузки завершатся ошибкой, старое хранилище не используется как запасное место записи.
2. Проверить доступ SDK, затем загрузку и скачивание тестового документа через API клиента и исполнителя. На время миграции остановить запись документов в выбранном окружении.
3. Запустить инвентаризацию с нужным `DATABASE_URL`. По умолчанию команда только читает счётчики:

```sh
npm run documents:migrate-storage
```

4. Создать проверенные копии и обновить ссылки. Указать абсолютный путь к журналу вне репозитория, в закрытом каталоге. Журнал имеет права `0600` и содержит служебные пути/идентификаторы документов:

```sh
npm run documents:migrate-storage -- --apply --journal=/absolute/private/path/document-migration.json
```

Скрипт охватывает `RequestContractFile`, `RequestDocumentRequest`, `RequestWorkStageFile`, `RequestWorkStageDocSlot`. Он сверяет размер и SHA-256 источника с БД, загружает с KMS, повторно читает и проверяет копию, затем условно обновляет ссылку только если исходный путь и контрольные данные не изменились. При ошибке исходный файл сохраняется; повторный запуск с тем же журналом продолжает операцию. Повреждённые/отсутствующие источники и изменившиеся строки требуют разбирательства; журнал нельзя удалять до завершения.

5. Проверить скачивание перенесённых документов и отсутствие старых ссылок. Очистку источников запускать только после сверки **всех окружений**, которые могли использовать старые ключи. Проверка скрипта охватывает только выбранную БД, поэтому локальный перенос не даёт основания удалить файлы рабочего окружения:

```sh
npm run documents:migrate-storage -- --cleanup --journal=/absolute/private/path/document-migration.json
```

Очистка ещё раз проверяет целевую копию, ссылку в БД и отсутствие старого ключа во всех четырёх таблицах выбранной БД, затем удаляет старые S3-версии и, для исторических договоров, совпадающий по хешу локальный файл. При отсутствии прав, несовпадении данных или оставшейся ссылке операция останавливается. Резервные копии старого хранилища очищаются отдельно по принятой политике хранения.

Имена бакета и сервисного аккаунта в Terraform сохранены для обновления без пересоздания ресурсов. Один приватный бакет и шифрование сами по себе не подтверждают соответствие всей системы 152-ФЗ.
