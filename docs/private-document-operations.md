## Подготовленные ресурсы

Корень: `infra/terraform/passports`. Существующие бакет документов, ключ и
runtime-аккаунт остаются на месте.

| Ресурс | Назначение |
| --- | --- |
| Аккаунт `*-document-audit` | Доставка журналов, без доступа к содержимому документов |
| Отдельный ключ AES-256 | Шифрование журналов, ротация 90 дней, защита от удаления |
| Приватный бакет `*-document-audit` | Только журналы в `events/`, лимит 1 GiB, без версионирования |
| Права на ключ, IAM и политика бакета | Доставке назначена роль `storage.uploader`, приложению явно запрещён доступ |
| Audit Trails | События управления каталогом; события данных только бакета документов и его KMS-ключа |
| Панель мониторинга | Объём двух бакетов, запросы документов, операции KMS, доставка и статус аудита |

Журналы удаляются lifecycle-правилом через 30 дней (`audit_retention_days`).
Это первоначальное эксплуатационное окно, а не срок, установленный законом.
Удаление lifecycle асинхронное. Для долгосрочного хранения и защиты от изменения
администратором потребуются отдельные решения; текущий журнал не является WORM.
Учитывать стоимость операций Audit Trails, хранения и ключа.

Второй бакет отделяет историю действий от данных, которые приложение может
удалять. Второй ключ исключён из фильтра аудита операций с ключом документов:
запись журнала не должна порождать бесконечный поток аудита самой себя.
Cloud Logging закрыт для новых клиентов с 22 октября 2026; новый log group
в этой конфигурации не создаётся.

Роль `storage.uploader` включает просмотр бакета и объектов; политика ограничивает
действия аккаунта аудита, а права расшифровки KMS-ключа ему не выдавались.
Аккаунту приложения отказаны листинг и удаление в тестовой проверке. Доставка
журнала и его шифрование проверены; отказ чтения реального объекта и отдельное
событие удаления документа ещё нужно подтвердить.

4. Для панели — `monium.dashboards.editor`; для чтения метрик —

   настройки оповещений — `monium.alerts.editor` и `monium.channels.editor`.

Роль сбора `audit-trails.viewer` назначается администратором отдельно:
Terraform не получает ради этого права администрирования всего каталога.
Настройки приложения и runtime S3-ключ для этой операции не меняются.

После назначения прав сформировать **новый** plan, проверить отсутствие удаления
и замены существующих ресурсов, затем apply. Старые `.tfplan` после bootstrap
не использовать. Секреты и state не коммитить.

```sh
env -u YC_TOKEN \
  YC_SERVICE_ACCOUNT_KEY_FILE="$HOME/.config/yandex-cloud/passports-terraform-key.json" \
  terraform -chdir=infra/terraform/passports plan -out=audit.tfplan
env -u YC_TOKEN \
  YC_SERVICE_ACCOUNT_KEY_FILE="$HOME/.config/yandex-cloud/passports-terraform-key.json" \
  terraform -chdir=infra/terraform/passports apply audit.tfplan
```

После apply проверить `ACTIVE`, записать и удалить синтетический объект через
`npm run passports:check-storage`, дождаться экспорта и проверить события
создания/удаления и KMS. Проверить фактическое шифрование объекта журнала,
отказ чтения/записи/удаления журнала runtime-аккаунтом и отсутствие обратной
связи, при которой аудит порождает собственные события. Убедиться, что графики
показывают реальные значения. Terraform validate/plan этого не доказывают.

Audit Trails Object Storage не перечисляет обычный `GetObject` среди событий.
Облачный аудит не заменяет прикладной `PassportAccessAudit` для чтений паспорта
исполнителем. Журналирование остальных чтений документов требует отдельной
проверки покрытия. В ключах объектов и логах не должно быть ФИО, реквизитов,
адресов и исходных имён файлов; служебные идентификаторы и IP тоже требуют
ограниченного доступа к журналам.

## Проверка доступности и задержек удаления

Из каталога `backend`:

```sh
npm run private-documents:check-health
```

Команда только читает БД и делает ограниченный листинг `passports/` и
`documents/`. Результат — JSON без ключей объектов и сведений пользователя;
код выхода `1` при ошибке доступа, БД или просрочке очистки.
Просрочка: 15 минут с `createdAt`; для `UNCOMMITTED_UPLOAD` сначала вычитается
час штатного ожидания. Перенос `notBefore` при повторе не обнуляет возраст.
Очередь относится к анкете и фото паспорта; её показатели не доказывают
успешное удаление всех видов документов заявки.

Успешный листинг не проверяет чтение/запись и KMS. Полная проверка выполняется
отдельной командой `npm run passports:check-storage` на синтетических данных.
В backend подготовлен выключенный по умолчанию издатель метрик. При задании
`PRIVATE_DOCUMENT_MONIUM_PROJECT=folder__<folder-id>` и секретного
`PRIVATE_DOCUMENT_MONIUM_APPLICATION_KEY` он делает проверку раз в минуту и
отправляет агрегаты в Monium Push JSON: `private_documents_storage_reachable`,
`private_documents_database_reachable`, `private_documents_health_check`,
`private_documents_heartbeat`, `passport_cleanup_pending`,
`passport_cleanup_overdue`, `passport_cleanup_oldest_seconds`. Данные анкеты,
ключи файлов и идентификаторы пользователей не отправляются. При ошибке БД
значения очереди не передаются, вместо фиктивных нулей публикуется недоступность
БД. Если проверка или процесс зависнут, отсутствует свежий heartbeat — для него
необходимо настроить отдельное оповещение об отсутствии данных.

Проверено на текущем API: массив `sensors` из примера документации возвращал
HTTP 200 с `sensorsProcessed: 0`, поэтому издатель использует массив `metrics`
и требует подтверждения обработки каждой метрики. Проверочная метрика
`notification_delivery_test` отделена от прикладных метрик по имени.
Проверка 6 ноября показала, что сервис `private-documents` пока возвращает
`UNKNOWN_SHARD`, а существующий `private-documents-validation` принимает семь
прикладных метрик. Этот работающий сервис выбран по умолчанию; после создания
отдельного рабочего сервиса можно изменить `PRIVATE_DOCUMENT_MONIUM_SERVICE`.
Правила фильтруют конкретное имя метрики.

Создать в Monium ключ приложения для проекта каталога с областью **Метрики**;
он разрешает запись в один проект и не предоставляет чтения или управления.
Хранить секрет вне Git, передать через секреты окружения сервера, не через
Terraform state. Запускать этот издатель пока только в одном экземпляре backend:
иначе несколько процессов будут писать в одну серию, а независимый отказ может
быть скрыт здоровым экземпляром. Перед многократным масштабированием добавить
идентификатор экземпляра и соответствующие алерты.

На сервере нужно включить публикацию, проверить появление и пропажу heartbeat,
отдельно вызвать ошибки доступа и БД, затем настроить и проверить правила
срабатывания и восстановления. Ни при каких обстоятельствах не считать локальные
юнит-тесты или ручную проверку подключённым мониторингом.

После задания двух переменных окружения на сервере выполнить из `backend`
`npm run private-documents:publish-health`. Команда проверяет реальную БД и
хранилище, отправляет один набор метрик и выводит только четыре булевых итога,
без секретов и данных пользователей. Это проверка подключения; постоянная
публикация начнётся только после развёртывания backend с этим кодом.

## Правила оповещений для следующего шага

| Сигнал | Первоначальное условие |
| --- | --- |
| Неполадки доступа к хранилищу или БД | Два неуспешных health-запуска подряд |
| Зависшее удаление паспорта | `cleanup.overdue > 0` |
| Проверка не запускается | Нет результата health-проверки более 3 минут |
| Заполненность любого бакета | Предупреждение 80%, критическое 90% лимита |
| Состояние Audit Trails | Статус ERROR; отдельно отсутствие метрики |
| Задержка доставки аудита | Есть принимаемые события, нет доставленных более 15 минут |

Для прикладных правил выбрать проект `folder__b1gcdvf6jupvtiqplmo6`, кластер
`default`, сервис из `PRIVATE_DOCUMENT_MONIUM_SERVICE` и метрику по полю `name`.
Правило неполадок проверяет `private_documents_health_check < 0.5` на двух
последовательных минутных точках; для диагностики рядом доступны
`private_documents_storage_reachable` и `private_documents_database_reachable`.
Правило очистки проверяет `passport_cleanup_overdue > 0` и не трактует отсутствие
этой метрики при недоступной БД как нулевую очередь. Для heartbeat выбрать
`private_documents_heartbeat` и отправку статуса `No data` после трёх минут
без точек. Для каждого правила назначить `Документы — support`, включить
уведомления о тревоге и восстановлении и проверить доставку после первого
развёртывания. Правила пока не созданы.

Нулевая доставка при отсутствии событий нормальна. Нет данных — отдельное
состояние, а не подтверждение исправности. Пороги уточняются по реальным метрикам.
Стандартные метрики бакета не содержат счётчика HTTP 5xx: такой алерт нельзя
создавать на придуманное имя метрики. Ошибки операций потребуют прикладных метрик
либо проверки синтетической операции.

Email-канал Monium адресуется учётной записи облака. Получателю нужно включить
Мониторинг и указать email в настройках уведомлений консоли; одного произвольного
email недостаточно. Тестовые уведомления о срабатывании и восстановлении
доставлены; повторную отправку и срабатывание рабочих алертов необходимо
проверять отдельно.
