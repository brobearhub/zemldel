# Бизнес-логика приложения `new-gorisons`

## Назначение документа

Этот документ является главным источником истины по бизнес-логике приложения.

Он нужен, чтобы:
- зафиксировать продуктовую модель;
- описать роли, сущности и правила доступа;
- отделить реализованное поведение от целевого;
- дать Cursor опору для безопасного развития доменной логики.

Если код противоречит этому документу:
- для бизнес-решений приоритет у этого документа;
- для технических деталей реализации нужно сверяться с кодом.

## Что это за продукт

`new-gorisons` - это платформа услуг.

На платформе есть два основных режима пользователя:
- заказчик: ищет и просматривает услуги;
- профессионал / поставщик услуг: создает профессиональный профиль и управляет услугами от имени этого профиля.

Текущая продуктовая модель:
- публичная часть показывает каталог услуг;
- зарегистрированный пользователь может остаться обычным заказчиком;
- зарегистрированный пользователь может создать профессиональный профиль;
- профессиональный профиль может быть личным (`SELF_EMPLOYED`) или корпоративным (`COMPANY`);
- все управляемые профессиональные данные принадлежат конкретному `Provider`.

## Основные роли

В системе есть два уровня ролей.

### Системные роли

Системная роль действует на всю платформу и хранится в `User.systemRole`.

Поддерживаются роли:
- `PLATFORM_ADMIN` - администратор платформы;
- `CUSTOMER` - обычный пользователь.

Правила:
- новый пользователь по умолчанию создается как `CUSTOMER`;
- `PLATFORM_ADMIN` имеет полный доступ ко всем данным платформы;
- системная роль не заменяет membership внутри provider, а существует параллельно с ним.

### Роли внутри provider

Доступ к данным поставщика выдается через `ProviderMember`.

Поддерживаются роли:
- `OWNER` - владелец профессионального профиля;
- `MANAGER` - менеджер профессионального профиля.

Статусы membership:
- `INVITED`;
- `ACTIVE`;
- `SUSPENDED`.

В доступе участвуют только membership со статусом `ACTIVE`.

## Основные сущности домена

### User

Пользователь платформы.

Ключевые поля:
- `id`;
- `email`;
- `name`;
- `systemRole`;
- `activeProviderId`.
- `customerCityId` (опционально) — выбранный город пользователя как заказчика (ссылка на справочник `City`).

Смысл:
- пользователь может быть только заказчиком;
- пользователь может состоять в одном или нескольких provider;
- `activeProviderId` задает текущий рабочий контекст профессионала.

### Provider

Профессиональный профиль поставщика услуг.

Ключевые поля:
- `id`;
- `name`;
- `slug`;
- `type`;
- `ownerUserId`.
- `cityId` (опционально) — город провайдера (ссылка на справочник `City`).

Типы:
- `SELF_EMPLOYED` - самозанятый / физлицо;
- `COMPANY` - компания / организация.

Смысл:
- это бизнес-сущность, от имени которой публикуются и управляются услуги;
- именно `Provider` является владельцем provider-данных;
- один пользователь может иметь membership в нескольких provider.

### Юридические профили и договоры

Юридические реквизиты сторон хранятся отдельно от текста договора и используются для автоподстановки переменных в шаблоны.

Ключевые сущности:
- `ProviderLegalProfile` — реквизиты provider-профиля: ИНН, КПП, ОГРН/ОГРНИП, юридический и почтовый адрес, банковские реквизиты, ФИО/должность подписанта.
- `CustomerLegalProfile` — реквизиты заказчика: ФИО, ИНН при наличии, адрес регистрации, почтовый адрес и контактные данные.
- `PassportDocument` — зашифрованный паспортный документ пользователя. Паспортные данные не дублируются в открытых юридических профилях; доступ к ним идет через документный контур и аудит.
- `ContractBlock` / `ContractBlockVersion` — библиотека шаблонных блоков договора, которой управляет только `PLATFORM_ADMIN`.
- `ContractTemplate` — provider-owned шаблон договора на документной модели редактора.
- `ContractInstance` — снимок договора по конкретной заявке/заказу.
- `ContractCommentThread` / `ContractComment` — inline-комментарии к фрагментам договора.

Правила:
- provider (`OWNER`/`MANAGER` активного provider) может создавать и редактировать свои шаблоны и черновики договоров;
- customer может читать только отправленные ему договоры и оставлять inline-комментарии, но не менять текст договора;
- `PLATFORM_ADMIN` управляет только библиотекой шаблонных блоков и не работает в provider-контексте договора;
- при создании `ContractInstance` система фиксирует snapshot автоподставленных значений (`variableSnapshot`), чтобы подписанный договор не менялся после будущих правок профилей;
- комментарии клиента привязаны к anchor в документе (block id/range/quote), могут получать ответы provider и закрываться после обработки;
- подписанный договор не редактируется; изменение текста после отправки сбрасывает подписи и возвращает договор в `DRAFT`.

### ProviderMember

Связь между пользователем и provider.

Ключевые поля:
- `providerId`;
- `userId`;
- `role`;
- `status`.

Смысл:
- определяет права пользователя внутри конкретного provider;
- один пользователь не может иметь дубликат membership в одном provider.

### Service

Карточка услуги, публикуемой на платформе.

Ключевые поля:
- `id`;
- `categoryId`;
- `status`;
- `title`;
- `price`;
- `description`;
- `providerId`;
- `createdByUserId`;
- `updatedByUserId`.

Смысл:
- каждая услуга всегда принадлежит конкретному provider;
- услуга не существует вне provider-контекста;
- услуга является публичной продажной единицей provider;
- публикация услуги управляется через жизненный цикл статусов;
- поля аудита должны сохранять, кто создал и кто последним менял запись.

Жизненный цикл услуги:
- `DRAFT` - черновик, не виден в публичной витрине;
- `PUBLISHED` - опубликованная услуга, доступна клиентам;
- `ARCHIVED` - архивная услуга, не участвует в публичной выдаче, но сохраняется в истории.

### ServiceRequest

Единая **заявка** клиента. Эта сущность объединяет то, что раньше жило как «заявка», «объявление» и «заказ».

Ключевые поля:
- `id`;
- `serviceId` (опционально) — если заявка создана со страницы услуги;
- `categoryId` (опционально) — если заявка создана с главной страницы по выбранной категории;
- `providerId` (опционально) — **провайдер заказа** (выставляется:
  - сразу для заявки по услуге (`SERVICE`);
  - для свободной/категорийной — только после того, как заявка стала заказом);
- предварительный выбор исполнителей (до заказа):
  - `ServiceRequestProviderOffer` — запись по паре (`serviceRequestId`, `providerId`) со статусом выбора;
  - заказчик может выбрать **несколько** провайдеров параллельно (мультивыбор);
  - выбранный провайдер может:
    - **принять** (кнопка «Начать работу с клиентом») → заявка становится заказом (`status=ACTIVE`, фиксируется `providerId`, чаты с остальными провайдерами блокируются правилами доступа);
    - **отказать** (кнопка «Отказать») → предложение по этому провайдеру помечается как `DECLINED`, заказчик может выбрать других/повторить выбор;
- `customerUserId` — аккаунт заказчика (в MVP обязателен для чата);
- город заявки:
  - `requestCityId` (опционально) — город, явно выбранный в форме заявки;
  - если `requestCityId` не указан, берём `User.customerCityId`;
  - для матчинга используется **регион/область** города, а не точный город;
- контакты/контекст (snapshot в момент создания заявки): `customerName`, `customerEmail`, `customerPhone`, `message`, `location`;
- `status`;
- `lockedAt` (момент фиксации заказа: когда заявка стала заказом и был назначен `providerId`);
- `createdAt`, `updatedAt`.

Правила видимости (лента провайдера):
- **Заявка по услуге** (`serviceId != null`) — доступна только провайдеру-владельцу услуги.
- **Свободная заявка** (`serviceId == null && categoryId == null`) — видна провайдерам, у которых совпадает **регион/область** (по региону города заявки и города провайдера).
- **Заявка по категории** (`serviceId == null && categoryId != null`) — видна провайдерам, у которых:
  - совпадает регион/область;
  - и есть хотя бы одна `Service(PUBLISHED)` в этой `categoryId`.

Жизненный цикл (единый):
- `NEW` — новая заявка;
- `DISCUSSING` — уже есть хотя бы один диалог;
- `TERMS_AGREED` — согласование условий: зафиксированы существенные условия сделки (цена/сроки/объём);
- `PROVIDER_SELECTED` — исполнитель выбран заказчиком (финальный выбор одной стороны сделки);
- `CONTRACT_ACCEPTED` — договор заключен (акцепт оферты + подтверждение условий сделки в интерфейсе);
- `ACTIVE` — в работе (исполнение началось после заключения договора);
- `SERVICE_RENDERED` — услуга оказана (исполнитель заявил о завершении);
- `ACCEPTANCE_PENDING` — ожидает принятия результата заказчиком (заказчик должен принять работу или отправить замечания);
- `ACCEPTED` — результат принят (в том числе автоматически, если заказчик не ответил в установленный срок);
- `COMPLETED` — завершен (сделка закрыта);
- `CANCELLED` — заказ отменён;
- `CLOSED` — заявка закрыта без сделки.

Примечания по юридически значимым шагам:
- **Согласование условий (`TERMS_AGREED`)**: фиксируется snapshot условий сделки (цена/сроки/объём). Это обязательная стадия перед договором.
- **Акцепт (`CONTRACT_ACCEPTED`)**: пользователь совершает действие, однозначно свидетельствующее о согласии (кнопка + чекбокс), что признается простой электронной подписью. При акцепте фиксируется **версия оферты**.
  - Для повышения юридической устойчивости **перед ПЭП требуется step-up аутентификация через Госуслуги** (см. раздел «Аутентификация: подключаемые провайдеры и step-up»).
- **Принятие результата (`ACCEPTANCE_PENDING` → `ACCEPTED`)**: заказчик либо принимает результат, либо отправляет замечания. Замечания возвращают заказ в `ACTIVE` (доработка) и цикл может повторяться.
- **Автопринятие**: если заказчик не ответил **7 дней** после `ACCEPTANCE_PENDING`, результат считается принятым автоматически (переход в `ACCEPTED`).
- Примечание: оплата/эскроу/выплаты не являются частью продуктового флоу (расчёты происходят вне платформы).

Публичная оферта:
- Канонический текст оферты хранится в [`docs/public-offer-2026-04-19.md`](docs/public-offer-2026-04-19.md).
- При переходе в `CONTRACT_ACCEPTED` система обязана сохранить, **какую версию оферты** принял заказчик (например `offerVersion=2026-04-19`).

Оплата/расчёты не моделируются в домене заявки: платформа не резервирует средства и не инициирует выплаты.

### ServiceCategory

Категория услуг — справочник с иерархией (как папки).

Ключевые поля:
- `id`;
- `name`;
- `slug`;
- `parentId` (опционально, для вложенности);
- `sortOrder` (опционально, для стабильной сортировки);
- `placements` — где категорию можно показывать в публичном UI (например `HOME`).

Смысл:
- категории используются для услуг провайдеров (`Service.categoryId`);
- дерево категорий отражает смысловую вложенность (как на Avito или в файловой системе);
- категории создаёт/редактирует/удаляет `PLATFORM_ADMIN`.

### Legacy-сущности (исторически)

Исторически в коде/БД могли существовать отдельные сущности `ServiceLead`, `ServiceAnnouncement` и `Order`.
Целевая продуктовая модель — **единая** `ServiceRequest`, а «заказ» является **фазой** заявки (`ServiceRequest.status in {ACTIVE, COMPLETED, CANCELLED}`).

### Чат по заявке (Conversation / Message)

Переписка между заказчиком и провайдером привязана к **одной заявке** (`ServiceRequest`) через `Conversation.serviceRequestId`.

Треды:
- для `SERVICE` — один тред на заявку (фактически уникальная пара `(serviceRequestId, providerId)` и `providerId` фиксирован);
- для заявок без `serviceId` (свободная/по категории) — **несколько тредов**: один тред `Conversation` на пару (`serviceRequestId`, `providerId`); параллельные диалоги допустимы, пока заявка **не стала заказом** (`status` не в `{ACTIVE, COMPLETED, CANCELLED}`).

**Доступ:**
- чат **недоступен**, пока у заявки **нет** `customerUserId`;
- **заказчик** — только если `ServiceRequest.customerUserId` совпадает с текущим пользователем;
- **provider** — пользователь с **ACTIVE** `ProviderMember` по `Conversation.providerId`;
- если заявка в статусе `ACTIVE/COMPLETED/CANCELLED` и `ServiceRequest.providerId != Conversation.providerId`:
  - **для заказчика** доступ к треду запрещён (заказ-режим: остаётся только выбранный провайдер);
  - **для провайдера** доступ к треду **разрешён только на чтение** (история переписки доступна как архив), но **отправка новых сообщений запрещена**; UI должен явно показать, что клиент оформил заказ с другой компанией;
- **`PLATFORM_ADMIN`** в MVP **не** имеет доступа к чужим чатам.

**Сообщения:** плоская лента по времени; опциональный ответ на сообщение через `replyToMessageId` (превью в UI). Идемпотентность отправки: пара `(conversationId, senderUserId, clientMessageId)`.

**Прочтение:** при открытии экрана чата — `mark read` (`lastReadAt = now()`); непрочитанные считаются по сообщениям с `createdAt > lastReadAt`. На списках заявок/заказов — **бейдж-счётчик** (в т.ч. обновление через Socket.io `chat.unreadHint` в комнате `user:{userId}` и компактный REST `unread-by-lead` для гидратации).

**Real-time:** Socket.io; handshake с JWT (выдача через BFF); полные события `message.created` в комнате `conversation:{id}` при открытом чате; лёгкие `chat.unreadHint` в `user:{userId}` для бейджей по другим тредам.

Примечание: старая терминология «чат по объявлению» соответствует заявкам без `serviceId` и использует те же правила тредов и locked-доступа.

## Главные бизнес-правила

### Общие правила

- Гость может просматривать публичные услуги.
- Зарегистрированный пользователь может пользоваться платформой как заказчик без создания provider.
- Создание provider - это отдельный onboarding-шаг после регистрации.
- Пользователь может переключать активный provider, если у него больше одного membership.
- Все provider-зависимые данные должны быть привязаны к `providerId`.

### Справочник локаций (City)

В продукте используется офлайн-справочник локаций РФ, импортируемый из ГАР/ФИАС.

Сейчас в справочник попадают адресные объекты уровней ГАР:
- `2`, `3`, `4`, `6` — административные/муниципальные единицы, поселения и населённые пункты;
- `5` — города (`г`);
- `1` — только города федерального значения (в ГАР это тоже `г`, но на уровне субъекта).

Улицы/дома/помещения и другие уровни ниже населённого пункта в продукт не импортируются.

Правила:
- локация выбирается из списка (автокомплит), без ручного freeform ввода;
- локация заказчика хранится отдельно от локации провайдера:
  - `User.customerCityId` — локация пользователя в клиентском контексте;
  - `Provider.cityId` — локация активного провайдера в профессиональном контексте;
- справочник обновляется вручную запуском скрипта импорта;
- команды:
  - первичная загрузка: `backend` → `npm run cities:update -- --mode full` (скачивает официальный `gar_xml.zip` ~50+ GB; по умолчанию в `/Volumes/One Touch/Projects/novagor/cities`, либо в ваш путь через `--out`);
  - обновление: `backend` → `npm run cities:update` (скачивает `gar_delta_xml.zip` и делает upsert изменений);
- при расширении списка импортируемых уровней нужен backfill через `--mode full` (дельта-архив не содержит полный перечень объектов, только изменения);
- ГАР/ФИАС не содержит координаты; координаты/геопоиск — отдельный слой (позже).

### Правила для provider

- При создании provider автоматически создается membership автора с ролью `OWNER` и статусом `ACTIVE`.
- При создании provider пользователю автоматически выставляется `activeProviderId` на новый provider.
- `SELF_EMPLOYED` provider не может иметь менеджеров.
- Один пользователь не может владеть более чем одним `SELF_EMPLOYED` provider.
- Добавлять менеджеров может только `OWNER`.
- Membership со статусом не `ACTIVE` не дает доступа к provider-данным.

### Правила для услуг

- Любая услуга обязана иметь `providerId`.
- `providerId` для create/update/delete не должен считаться достоверным, если пришел с клиента.
- Provider-контекст для защищенных операций определяется из пользователя и его активного membership.
- Нельзя обновлять или удалять provider-данные только по `id` без проверки области доступа.
- Публичный каталог услуг доступен всем.
- В публичной витрине показываются только услуги со статусом `PUBLISHED`.
- Услуги со статусами `DRAFT` и `ARCHIVED` не должны отображаться клиентам.
- Управление услугами доступно только пользователям с подходящей ролью в provider или платформенным администраторам.
- Услуга сначала может быть создана как черновик, затем опубликована или отправлена в архив.
- Архивирование предпочтительнее физического удаления, если нужно сохранить историю работы provider.

Дополнительные правила для шаблонов и категорий:
- `ServiceCategory` — платформенный справочник: CRUD доступен только `PLATFORM_ADMIN`.
- На главной странице:
  - сначала показываются категории с `placements` включающим `HOME`;
  - затем показываются опубликованные услуги провайдеров.

### Правила для заявок и заказов

- Первый отклик клиента на услугу - это заявка, а не обязательный немедленный заказ.
- Заявка создается по опубликованной услуге.
- Гость может инициировать создание заявки из публичной услуги, но перед фактической отправкой заявки должен пройти регистрацию или вход.
- После успешной аутентификации в сценарии заявки система должна продолжить отложенный flow и создать заявку уже от имени авторизованного пользователя.
- Если заявка создана после auth-gated сценария из публичной услуги, пользователь должен попасть в личный кабинет на раздел своих заявок.
- Заказ является следующим этапом после заявки, а не обязательной стартовой сущностью.
- Поток продаж продукта фиксируется как `услуга -> заявка -> заказ`.
- До финального выбора исполнителя заявка может вестись параллельно с несколькими провайдерами (несколько диалогов и предварительный выбор через provider offers).
- **Заказ — это фаза заявки**, а не отдельная сущность: заявка считается «заказом» начиная со статуса `PROVIDER_SELECTED` и далее по жизненному циклу.
- Переход в заказную фазу (`PROVIDER_SELECTED`) возможен только для заявки, привязанной к авторизованному заказчику через `customerUserId`.
- После `PROVIDER_SELECTED` заявка становится эксклюзивной: фиксируется `providerId`, а остальные диалоги переходят в read-only архив (см. правила доступа в разделе чата).
- Списки «заявок» и «заказов» в UI — это разные представления одной сущности по статусам (а не отдельные таблицы).

Дополнительные правила для объявлений:
- Объявление может быть переведено в заказ **минуя заявку**.
- Заказ, созданный из объявления, остаётся provider-scoped сущностью и должен появиться в списках заказов и заказчика, и провайдера.
- При конверсии объявления в заказ сервер сам определяет `providerId` из контекста провайдера и `customerUserId` из объявления.

### Правила для чата

- Для `SERVICE` заявки тред один (уникальная пара `(serviceRequestId, providerId)`; `providerId` фиксирован).
- Для свободных/категорийных заявок допускаются **несколько тредов**: по одному `Conversation` на пару `(serviceRequestId, providerId)` до момента, когда заявка стала заказом.
- Создание треда — идемпотентный `POST ensure` при открытии UI чата (не от первого сообщения как единственного триггера).
- Отправлять сообщения могут только участники треда (заказчик по заявке или ACTIVE член provider этой заявки).
- Счётчики непрочитанных на списках синхронизировать с сервером (REST + события); не доверять только клиентскому инкременту без периодической сверки.

## Пользовательские сценарии

### Гость

Гость может:
- открыть главную страницу;
- просматривать список услуг;
- открыть страницу отдельной услуги;
- перейти к регистрации или входу.

Гость также может:
- открыть страницу категории услуг;
- увидеть список исполнителей (провайдеров/услуг), которые оказывают услуги в этой категории;
- перейти на страницу конкретной провайдерской услуги и оставить заявку.

Гость не может:
- управлять услугами;
- работать с provider;
- открывать защищенные профессиональные сценарии.

### Регистрация и вход

Сценарий регистрации:
1. Пользователь вводит имя, email и пароль.
2. Создается аккаунт.
3. Пользователь автоматически логинится.
4. По умолчанию после регистрации пользователь направляется на создание provider.
5. Исключение: если регистрация была начата из auth-gated сценария создания заявки по услуге, система должна вернуть пользователя в customer-flow и завершить создание заявки вместо перехода на provider onboarding.

Сценарий входа:
1. Пользователь вводит email и пароль.
2. Если данные корректны, создается сессия.
3. По умолчанию после входа пользователь попадает на главную страницу.
4. Исключение: если вход был начат из auth-gated сценария создания заявки по услуге, система должна вернуть пользователя в customer-flow и завершить создание заявки.

### Аутентификация: подключаемые провайдеры и step-up

В системе есть:
- **основной способ входа**: логин/пароль (credentials);
- **подключаемые провайдеры входа** (MVP: Госуслуги) — управляются в профиле пользователя.

Step-up аутентификация:
- для юридически значимых действий (MVP: акцепт оферты / `CONTRACT_ACCEPTED`, подписание договоров) требуется **дополнительная** аутентификация через Госуслуги;
- step-up не заменяет основную сессию, а фиксируется как отдельное «подтверждение личности» с политикой свежести (например, не старше 15 минут).

Примечание по MVP:
- до подключения реального API Госуслуг используется **мок‑провайдер** (техническая заглушка), но доменная модель и UI должны быть готовы к реальной интеграции.

### Onboarding профессионала

После регистрации пользователь попадает на экран создания профессионального профиля.

На этом шаге он может:
- создать provider;
- пропустить шаг и остаться обычным заказчиком.

Если пользователь создает provider:
1. Заполняет `name`, `slug`, `type`.
2. Система создает `Provider`.
3. Система создает `ProviderMember(role=OWNER, status=ACTIVE)`.
4. Система выставляет `activeProviderId`.
5. Пользователь попадает в профиль.

Если пользователь пропускает шаг:
- аккаунт остается обычным пользовательским аккаунтом без provider-membership;
- позже можно вернуться к созданию provider из профиля.

### Профиль пользователя

Профиль пользователя - это личный кабинет, в котором пользователь действует как частное лицо / заказчик.

В личном кабинете находятся:
- личные данные аккаунта;
- пользовательские заявки как заказчика;
- статус аккаунта;
- пользовательские заказы как заказчика;
- документы заказчика (MVP: паспорт);
- вход в профессиональный кабинет, если у пользователя есть хотя бы один `ACTIVE` membership.

Текущее состояние:
- личный профиль реализован как обзор аккаунта;
- customer-заявки должны отображаться отдельным разделом внутри личного кабинета;
- часть provider-функций пока еще находится внутри страницы профиля как переходное решение;
- customer-заказы отображаются отдельным разделом внутри личного кабинета как MVP-история заказов;
- подробный workflow заказа пока остается минимальным и не считается завершенной бизнес-функцией.

### Документы заказчика: паспорт (MVP)

Назначение:
- хранить паспортные данные заказчика в системе для случаев, когда они необходимы **только после заключения сделки**.

Хранение:
- паспортные данные должны храниться в БД **только в зашифрованном виде** (шифртекст);
- любые операции расшифровки должны оставлять **аудит‑след**.

Доступ к расшифрованным данным:
- **заказчик**: может читать/обновлять/удалять свой паспорт;
- **провайдер**: может читать паспорт заказчика **только если** есть заказ/сделка с этим заказчиком, и паспорт требуется для выполнения заказа (в MVP — минимум после `CONTRACT_ACCEPTED`, по заказу где `ServiceRequest.providerId` совпадает с провайдером).

Безопасность:
- администратор платформы в MVP не должен иметь UI‑доступа к паспортным данным;
- для операций просмотра/подписания/юридически значимых подтверждений может применяться step-up через Госуслуги.

### Разделение личного и профессионального кабинета

В системе используется один аккаунт пользователя, но два разных интерфейсных контекста:
- личный кабинет пользователя;
- профессиональный кабинет поставщика услуг.

Главный принцип:
- система не делит пользователей на два разных аккаунта;
- пользователь всегда имеет один аккаунт, одну сессию и один набор учетных данных;
- разделяется не аккаунт, а рабочий контекст.

Контексты работы:
- в личном кабинете пользователь действует от своего имени;
- в профессиональном кабинете пользователь действует от имени активного `Provider`.

### Профессиональный кабинет

Профессиональный кабинет - это отдельный workspace внутри продукта, в котором пользователь работает как provider.

Профессиональный кабинет строится вокруг `activeProviderId`.

В профессиональном кабинете находятся:
- обзор активного provider;
- управление услугами provider;
- управление командой provider;
- профессиональные заявки / заказы;
- документы provider (MVP: договоры);
- настройки provider;
- переключение между provider, если у пользователя несколько membership.

Правила навигации:
- если у пользователя нет provider-membership, профессиональный кабинет ему недоступен как рабочее пространство;
- если у пользователя есть хотя бы один `ACTIVE` membership, в интерфейсе показывается вход в профессиональный кабинет;
- если у пользователя один provider, кабинет открывается сразу в его контексте;
- если у пользователя несколько provider, кабинет открывается в контексте `activeProviderId`, а переключение provider происходит внутри профессионального кабинета.

Что не должно развиваться внутри обычного профиля:
- управление услугами provider;
- управление участниками команды provider;
- профессиональные заявки и бизнес-процессы provider;
- аналитика и рабочие инструменты provider.

Эти сценарии должны развиваться внутри отдельного профессионального кабинета.

### Документы провайдера: договоры (MVP)

Цель:
- дать провайдеру возможность создавать и редактировать **шаблоны договоров** и формировать **экземпляры договоров** по конкретным сделкам/заказам.

Правила:
- договоры являются provider-scoped ресурсами (все записи принадлежат конкретному `providerId`);
- поддерживаются «ответвления» (fork) от существующих шаблонов для быстрого создания новых;
- перед подписанием договоров применяется **ПЭП**, но с обязательным step-up через Госуслуги;
- MVP не предполагает загрузку Word/Excel; вместо этого используется редактор (структурированный текст + переменные).

Подстановка данных:
- шаблон поддерживает плейсхолдеры (переменные), которые при формировании экземпляра подставляются данными:
  - провайдера (название, реквизиты и т.п. — по мере появления полей в модели provider),
  - заказчика (минимум: имя/email; паспорт — только при наличии права доступа),
  - условий сделки (`dealTerms`) и идентификаторов заказа.

### Работа профессионала

Если у пользователя есть хотя бы один `ACTIVE` membership:
- он считается профессионалом;
- у него есть активный профессиональный профиль;
- он может работать в контексте текущего `activeProviderId`.

Профессионал может:
- просматривать активный provider;
- переключать активный provider;
- просматривать участников активного provider;
- если он `OWNER`, добавлять менеджеров;
- если его роль допускает управление услугами, работать с услугами provider.

### Управление командой

Для `COMPANY` provider:
- `OWNER` может добавить менеджера по email существующего пользователя;
- если membership уже есть, запись может быть обновлена до `MANAGER` + `ACTIVE`, если это допустимо;
- владелец не может добавить самого себя как менеджера;
- владелец не может быть понижен этим сценарием до менеджера.

Для `SELF_EMPLOYED` provider:
- команда не поддерживается;
- добавление менеджеров запрещено.

### Управление услугами

Есть два режима работы с услугами.

Публичные сценарии:
- список услуг;
- просмотр карточки услуги.

Защищенные сценарии:
- чтение списка своих услуг;
- создание услуги;
- редактирование услуги;
- архивирование услуги;
- публикация услуги;
- перевод услуги обратно в черновик;
- удаление услуги как исключение, а не базовый рабочий сценарий.

Категории услуг (платформенная зона):
- `PLATFORM_ADMIN` управляет:
  - деревом категорий услуг (`ServiceCategory`);
  - настройкой `placements` для публичных страниц (например `HOME`).

Текущее правило ролей:
- `PLATFORM_ADMIN` может управлять всеми услугами;
- `OWNER` может читать, создавать, редактировать, публиковать, архивировать и удалять услуги своего активного provider;
- `MANAGER` может читать, создавать и редактировать услуги своего активного provider;
- `MANAGER` может переводить услугу в черновик и публиковать ее;
- `MANAGER` не должен удалять или архивировать услуги, пока это явно не изменено в бизнес-спецификации.

### Работа с заявками

В профессиональном кабинете заявки являются следующим рабочим уровнем после опубликованных услуг.

Provider должен иметь возможность:
- видеть новые заявки по своим услугам;
- вести диалог с заказчиком по заявке;
- видеть, что заказчик **выбрал его** (через `ServiceRequestProviderOffer(status=SELECTED)` для пары `(serviceRequestId, providerId)`);
- участвовать в согласовании условий и запуске сделки по юридически корректному workflow.

Поток сделки (юридически сильный):
- заказчик ведёт переговоры с провайдерами в чате (статусы `NEW` → `DISCUSSING`);
- провайдер формирует и отправляет заказчику **условия сделки** (цена/сроки/объём);
- заказчик подтверждает условия → заявка переходит в `TERMS_AGREED` (в `ServiceRequest` фиксируется snapshot условий);
- заказчик делает **финальный выбор исполнителя** (только один) → `PROVIDER_SELECTED`;
- заказчик выполняет **акцепт оферты** в интерфейсе (чекбокс + кнопка “Заключить договор и начать выполнение”) → `CONTRACT_ACCEPTED` (фиксируем `offerVersion` и факт акцепта);
- после заключения договора провайдер начинает выполнение → `ACTIVE`;
- по завершению провайдер отмечает “Услуга оказана” → `SERVICE_RENDERED`;
- провайдер отправляет результат на приемку → `ACCEPTANCE_PENDING` (ставим дедлайн автопринятия 7 дней);
- заказчик либо:
  - “Принять результат” → `ACCEPTED` → `COMPLETED`;
  - “Отправить замечания” → заявка возвращается в `ACTIVE` (доработка), затем цикл `SERVICE_RENDERED` → `ACCEPTANCE_PENDING` повторяется.

Правило по мультивыбору исполнителей:
- до стадии `PROVIDER_SELECTED` заказчик может общаться и предварительно выбирать несколько провайдеров через `ServiceRequestProviderOffer`;
- после `PROVIDER_SELECTED` и далее доступ к заявке/чату остаётся только у выбранного исполнителя (остальные треды переходят в read-only архив по правилам доступа).

### Работа с заказами

В MVP заказ — это **фаза заявки** (единая сущность), выделяемая по статусам (например начиная с `PROVIDER_SELECTED` и далее).

Provider должен иметь возможность:
- видеть заказы своего активного provider;
- различать активные, завершенные и отмененные заказы.

Заказчик должен иметь возможность:
- видеть свои заказы в личном кабинете;
- различать активные, завершенные и отмененные заказы.

## Правила доступа

### Базовые принципы

- UI не является источником истины по правам.
- Скрытие кнопки не считается защитой.
- Все реальные проверки должны выполняться на сервере.
- Доступ к provider-данным всегда должен учитывать provider scope.

### Active provider context

Для профессиональных операций используется активный provider-контекст.

Правило:
- если у пользователя есть `activeProviderId` и он валиден среди `ACTIVE` memberships, используется он;
- иначе используется первый доступный `ACTIVE` membership;
- если memberships нет, пользователь считается не имеющим provider-контекста.

### Scope-защита

Для любой provider-сущности:
- список должен фильтроваться по `providerId`;
- update/delete не должны выполняться по одному `id` без проверки принадлежности к `providerId`;
- при create `providerId` должен устанавливаться из серверного контекста пользователя.

## Что уже реализовано

На текущий момент реализовано:
- регистрация и вход;
- хранение системной роли пользователя;
- provider onboarding;
- создание provider;
- переключение активного provider;
- просмотр участников provider;
- добавление manager в `COMPANY` provider владельцем;
- публичный просмотр услуг;
- серверно защищенное управление услугами с учетом provider scope;
- хранение memberships и active provider в auth context / session;
- единый жизненный цикл заявки/заказа на базе статусов `Request` (переговоры → условия → выбор исполнителя → акцепт → исполнение → приемка → завершение);
- списки заказов для заказчика и provider.

## Что пока не является завершенной бизнес-логикой

Следующие области пока нельзя считать полноценной продуктовой логикой:
- заказы: реализован MVP-уровень; расширенный lifecycle и операционные сценарии только начинают появляться;
- платежи: **не поддерживаются** в продукте; расчёты между заказчиком и исполнителем происходят вне платформы;
- отзывы как самостоятельный пользовательский процесс отсутствуют;
- публичные страницы provider как отдельный продуктовый сценарий не оформлены;
- ранний CRUD услуг в приложении под `app/admin/services` не доведён до продуктового кабинета провайдера; целевая модель разделения: UI **`/admin/*`** — только платформеный админ (`PLATFORM_ADMIN`), кабинет провайдера — **`/pro/*`** (подробнее в `frontend/docs/roles-and-permissions.md`);
- детальная карточка заказа и расширенные действия с заказом пока не доведены до пользовательского UI.

- это не считается уже реализованной бизнес-логикой;
- Cursor не должен автоматически считать эти сценарии существующими в коде;
- до реализации каждая фича должна быть уточнена отдельной мини-спецификацией или обновлением этого документа.

Потенциальные направления развития:

Для заказчика и клиентского опыта:
- расширенный жизненный цикл заказов и дополнительные бизнес-статусы;
- детальная история заказов для заказчика и профессионала;
- отзывы и рейтинг после завершения заказа;
- создание клуба по интересам.
- настроить оптимизацию веб-сайта для улучшения его видимости и рейтинга на страницах результатов поисковых систем (SERP);
- настроить поисковую оптимизацию (SEO).

Инвестиции (земля):
- отдельный раздел про инвестиции в землю;
- **не услуги**: вместо каталога услуг — **объявления о продаже земельных участков** (листинг, карточка, поиск/фильтры);
- калькулятор инвестиций (входные параметры, расчёт доходности/окупаемости, сценарии).

Для профессионального кабинета и provider-инструментов:
- публичная страница provider с его услугами и описанием;
- выделение отдельного маршрута профессионального кабинета (`/pro` или аналогичного) вместо развития provider-функций внутри общего профиля;
- полноценный профессиональный кабинет под `/pro/*` вместо раннего dev/internal CRUD и с явным разделением от платформеной зоны `/admin/*`;
- расширенное управление командой provider;
- функционал и страницы (в клиентском и провайдерском интерфейсных контекстах) для постинга в соцсетях (VK, MAX, Telegram): публикация услуг провайдера, заявок/объявлений от клиентов (с ссылкой на сайт и текстом), информации о компании/провайдере; а также аналитика по откликам на посты;
- отдельная страница (инструмент) для расчёта KPI провайдера (`COMPANY` / `SELF_EMPLOYED`) **в разрезе каждой услуги** с учётом того, что сроки/циклы выполнения могут отличаться по услугам;
- лента заявок между провайдерами.

Для коммуникации и взаимодействия:
- статусы взаимодействия между заказчиком и профессионалом;
- уведомления о ключевых действиях в системе.

Примечание: **чат по заявке** описан в разделе «Чат по заявке» выше и реализуется в продукте; пункт roadmap про «чат между заказчиком и профессионалом» считается закрытым на уровне MVP данной спецификации.

Для AI и поддержки платформы:
- поиск услуги через чат с искусственным интеллектом;
- обратная связь: предложения по улучшению сайта, помощь, поддержка.

Правило при реализации roadmap:
1. Сначала описать целевой сценарий и ограничения в этом документе.
2. Затем определить роли, доступы и состояние данных.
3. Только после этого менять схему, API и UI.

## Ограничения домена

Не нужно предполагать в системе наличие следующих сущностей, если они не добавлены отдельной спецификацией:
- корзина;
- онлайн-оплата;
- заявка со сложным жизненным циклом;
- календарь бронирования;
- многоступенчатое согласование заказа;
- публичный рейтинг provider;
- сложная организационная иерархия компании.

Если такие функции понадобятся, они должны быть сначала описаны в этом документе, а потом реализованы в коде.

## Правила для Cursor

### Что считать источником истины

При изменении доменной логики Cursor должен опираться в первую очередь на:
1. `docs/business-logic.md`
2. `frontend/docs/roles-and-permissions.md`
3. текущую схему и реализацию, если они не противоречат этим документам

### Что Cursor должен делать

- Опирайся на текущую доменную модель: `User`, `Provider`, `ProviderMember`, `Service`, `ServiceLead`, `Order`, чат (`Conversation`, `Message`, `ConversationReadState`).
- Разделяй системные роли платформы и роли внутри provider.
- Любую provider-зависимую сущность связывай с `providerId`.
- Все серверные проверки доступа строй через provider context.
- Не доверяй `providerId`, пришедшему с клиента, в protected create/update/delete.
- Разделяй "уже реализовано" и "целевая логика", не выдавай заглушки за готовые продуктовые функции.
- Если меняется бизнес-логика, сначала обнови этот документ, потом код.

### Что Cursor не должен делать

- Не придумывай новые роли без обновления этого документа.
- Не добавляй новые статусы заказа, оплаты, сделки или бронирования без отдельной спецификации.
- Не считай страницы `app/admin/services` финальным кабинетом провайдера: целевой UX — `/pro/*`. Не путай UI `/admin/*` (платформа) с HTTP-префиксом `admin` на backend для provider-scoped API — смотри guard и `providerId`, не только путь.
- Не делай авторизацию только на уровне UI.
- Не разрешай update/delete provider-данных по одному `id` без scope-проверки.
- Не разрешай менеджеру удалять услуги, пока это явно не изменено в спецификации.
- Не добавляй менеджеров в `SELF_EMPLOYED` provider.
