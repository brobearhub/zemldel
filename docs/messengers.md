# Telegram и MAX: первая версия

Состояние на 2026-11-04: код и локальная миграция готовы. Реальные боты ещё не подключены:
токены отсутствуют в локальной конфигурации; production и доставка в мессенджеры не проверены.

## Боты и интерфейс

- Telegram: https://t.me/zemledel_agent
- MAX: https://max.ru/id6679190271_bot
- Клиент: `/profile?section=profile`, блок «Мессенджеры».
- Исполнитель: `/pro/settings`, тот же блок; привязка принадлежит личному User.
- Нажать «Подключить», затем «Открыть», запустить бота, вернуться на сайт и подтвердить аккаунт.
- Оба мессенджера могут быть подключены одновременно. Для переписки на сайте подключение необязательно.
- Ответ: кнопка «Ответить здесь» под уведомлением Telegram или MAX выбирает заявку для одного
  следующего текстового сообщения. Бот называет собеседника и номер заявки. Выбор действует
  10 минут; `/cancel` отменяет его, новая кнопка меняет адресата. Штатная функция «Ответить»
  на уведомлении тоже работает и имеет приоритет. Текст без выбранной заявки получает подсказку.
  Выбор хранится в БД; повторы событий не создают повторное сообщение и не меняют его адресата. Файлы, голосовые, редактирование, удаление и автоматические
  сообщения о действиях с заявкой в первую версию не входят.

## Обновление: кнопка «Ответить здесь»

После выкладки backend применить миграции (`npm run db:migrate:deploy`, если это не сделала
команда запуска) и перезапустить приложение. Затем в консоли backend выполнить
`npm run messengers:setup`: подписка MAX должна включать `message_callback`, а Telegram-webhook —
`callback_query`. В режиме Telegram polling новый список событий применяется самим backend.
Новых переменных окружения нет. Повторная привязка аккаунтов не нужна.

Две кнопки появятся у **новых** уведомлений. Старые сообщения автоматически не редактируются;
на них по-прежнему можно ответить стандартной функцией мессенджера. В MAX ответ на callback
сохраняет текст уведомления и обе кнопки, а инструкция отправляется отдельным сообщением.

Проверка после деплоя: отправить сообщение с сайта → нажать «Ответить здесь» в каждом
мессенджере → написать обычный текст → проверить единственный ответ в нужном чате сайта.

## Конфигурация backend

На frontend используется существующая переменная `NEXTAUTH_URL=https://zemledel.ru`.
Обработчик `/api/messengers` сверяет Origin изменяющих запросов с этим публичным адресом:
за reverse proxy внутренний URL Next.js может иметь другой hostname или протокол.
Токены ботов и webhook-секреты остаются только на backend.

В `backend/.env` локально и в серверных секретах при развёртывании:

```dotenv
TELEGRAM_BOT_USERNAME=zemledel_agent
TELEGRAM_BOT_TOKEN=<токен Telegram>
TELEGRAM_WEBHOOK_SECRET=<случайная строка 16–256 символов A-Z a-z 0-9 _ ->
MAX_BOT_USERNAME=id6679190271_bot
MAX_BOT_TOKEN=<токен MAX>
MAX_WEBHOOK_SECRET=<другая случайная строка>
MESSENGER_SITE_URL=https://zemledel.ru
MESSENGER_WEBHOOK_BASE_URL=https://<публичный адрес backend>
MESSENGER_WORKER_ENABLED=true
```

Публичные имена ботов и случайные webhook-секреты добавлены в локальный `.env`.
Секреты не выводятся в лог и не должны попадать в frontend или Git.
`MESSENGER_WORKER_ENABLED=false` выключает обработчик очереди; по умолчанию он выключен.
Для работы нужен постоянно запущенный процесс backend, PostgreSQL и исходящий HTTPS к Bot API.
При включённом worker одно соединение PostgreSQL постоянно слушает уведомления без запросов к очереди.
Если `DATABASE_URL` ведёт через PgBouncer в transaction-режиме, задайте
`MESSENGER_LISTEN_DATABASE_URL` с прямым адресом PostgreSQL или используйте session pooling.
Драйвер `pg`, уже используемый Prisma, объявлен прямой зависимостью для LISTEN; новых сервисов нет.

Порядок подключения (команды из `backend`):

```sh
npm run db:generate
npm run db:migrate:deploy
npm run build
# Запустить/перезапустить backend с заполненными переменными.
npm run messengers:check
npm run messengers:setup
```

Первый вызов только проверяет токен, имя бота и существующие webhooks. Второй регистрирует:

- `POST /messengers/TELEGRAM/webhook`, заголовок `X-Telegram-Bot-Api-Secret-Token`;
- `POST /messengers/MAX/webhook`, заголовок `X-Max-Bot-Api-Secret`.

Это команды администратора для однократной настройки интеграции. В консоли backend
на хостинге запускайте их из `/app/backend`, где находится `package.json`.
Они используют переменные окружения backend и локально установленный `tsx`; `npx` не нужен.
Обычный пользователь подключает свой аккаунт кнопками в профиле сайта.

Telegram API вызывается через `grammy`: проверка бота, чтение/регистрация webhook
и отправка сообщений. Все запросы Telegram используют IPv4 и HTTPS keep-alive.
По умолчанию `TELEGRAM_UPDATES_MODE=webhook`; получение через long polling включается отдельно.
Тайм-ауты: 15 секунд для настройки, 10 секунд для отправки, 35 секунд для polling API
(ожидание событий Telegram — 25 секунд); повторы доставки
выполняет существующая очередь. Ошибки SDK преобразуются в безопасные сообщения
без токенов, webhook-секретов и содержимого переписки; `retry_after` сохраняется.
MAX продолжает использовать свой HTTP API. Прокси пока не настроен:
grammY обращается к Telegram напрямую и не устраняет недоступность сети хостинга.

### Telegram через long polling

Для сервера, который может обращаться к Telegram, но недоступен для входящих Telegram-webhook:

1. Развернуть backend с поддержкой polling и переменными:
   ```env
   TELEGRAM_UPDATES_MODE=polling
   MESSENGER_WORKER_ENABLED=true
   ```
   Остальные переменные ботов, включая webhook-секреты, сохранить.
   `MESSENGER_WEBHOOK_BASE_URL=https://api.zemledel.ru` по-прежнему нужен для MAX
   и проверки, что существующий Telegram-webhook принадлежит этому приложению.
2. В консоли backend выполнить:
   ```sh
   npm run messengers:check
   npm run messengers:setup
   npm run messengers:check
   ```
   В режиме polling `setup` удаляет только Telegram-webhook с ожидаемым URL,
   с `drop_pending_updates=false`. Чужой URL скрипт не удалит.
   MAX продолжает настраиваться через webhook. `check` ничего не меняет;
   ожидаем `TELEGRAM: режим polling; webhook отключён`.
3. Backend автоматически начнёт опрос (до 30 секунд после удаления webhook).
   В логах: `Telegram long polling запущен через IPv4`.
   Обычным пользователям консоль не нужна: новая ссылка на сайте → запуск бота → подтверждение.

Polling — постоянно работающий фоновый процесс с одним ожидающим HTTP-запросом.
Он не меняет событийную очередь исходящих сообщений. Ошибки повторяются с задержкой
1–30 секунд (или дольше, если Telegram прислал `retry_after`). Наличие webhook
проверяется при получении блокировки; backend сам не удаляет его при запуске.
Ответы API 400/403 на отправку служебного сообщения записываются безопасным предупреждением
и не блокируют получение событий остальных пользователей.

Один экземпляр на бота получает PostgreSQL advisory lock через отдельное постоянное соединение.
Все реплики должны использовать одну БД; `MESSENGER_LISTEN_DATABASE_URL`/`DATABASE_URL`
должен вести напрямую в PostgreSQL или session pool, **не transaction pool**.
Соединение с БД проверяется перед каждым запросом событий; при его потере запрос прерывается,
при остановке backend блокировка освобождается. Резервная реплика пробует стать активной раз в 30 секунд.
Миграции БД для этого режима не нужны.

События обрабатываются последовательно и подтверждаются следующим `getUpdates` только после
обработки. После аварийного перезапуска возможен повтор последнего события: сообщения чата
дедуплицируются по `clientMessageId`, повторный `/start` того же аккаунта сохраняет привязку.
Служебное сообщение бота при повторе может прийти повторно. Telegram хранит события ограниченное
время; polling не устраняет длительную недоступность исходящего соединения.

Возврат к webhook: установить `TELEGRAM_UPDATES_MODE=webhook`, развернуть/перезапустить
все экземпляры backend (остановить poller), затем выполнить `npm run messengers:setup`.

Эти адреса должны быть доступны извне по HTTPS. Не направлять webhook на Next.js `/api/messengers`:
это отдельный авторизованный BFF настроек, он намеренно не проксирует события ботов.
Если бот уже подключён к другому URL, скрипт откажется его заменять. Сначала выяснить назначение
существующего подключения. Telegram `drop_pending_updates` не включается.

MAX использует `https://platform-api2.max.ru` и заголовок Authorization. Если сервер не доверяет
цепочке сертификатов API, установить необходимый доверенный CA (например через NODE_EXTRA_CA_CERTS),
не отключать проверку TLS.

## Хранение и гарантии

- `MessengerLinkToken`: хеш одноразового кода, срок 10 минут, предъявленный аккаунт и подтверждение.
  Новый код инвалидирует предыдущий. Подтверждать может только владелец авторизованной сессии.
- `MessengerConnection`: уникальные `(userId, platform)` и `(platform, externalUserId)`.
  Отключение удаляет привязку и её доставки; старые уведомления после перепривязки не принимаются.
- `Message` и `MessengerOutbox` создаются одной транзакцией внутри `ChatService.createMessage`.
- Очередь разворачивается в `MessengerDelivery` для доступных участников, кроме автора.
  Новая привязка не получает накопленные сообщения, созданные до её подключения.
- Событие входящего сообщения имеет стабильный UUID из платформы, диалога и внешнего ID сообщения.
  Повторная доставка вызывает существующий идемпотентный ChatService; права проверяются повторно.
- У каждой части длинного текста свой внешний ID, но ответ на любую часть связан с одним Message.
- Worker запускается по PostgreSQL LISTEN/NOTIFY: INSERT в `MessengerOutbox` будит обработчики
  только после COMMIT. Это одинаково работает для сообщений сайта и ответов через webhook.
  При пустой очереди таймера и запросов к таблицам нет. До 10 параллельных получателей за проход,
  одна доставка на подключение; конкурирующие процессы используют условные обновления и lease.
  Порядок сохраняется внутри подключения.
- После прохода вычисляется ближайшее время готовности первого задания каждого получателя с учётом
  Retry-After, lease и ограничения частоты; создаётся один одноразовый таймер. Новое уведомление
  запускает обработку раньше этого срока. Сигнал во время отправки не теряется: планируется ещё проход.
- После запуска backend и переподключения LISTEN выполняется проверка накопленных заданий.
  NOTIFY не является хранилищем: пропущенное уведомление восстанавливается из outbox.
  При ошибке БД/обрыве соединения выполняются повторы восстановления с задержкой от 1 до 60 секунд;
  после восстановления и опустошения очереди эти таймеры также прекращаются.
- До 8 попыток, экспоненциальная задержка с учётом Retry-After, HTTP timeout 10 секунд.
  Ошибки доступа отменяют доставку; блокировка бота отмечается в настройках.
- Статусы: PENDING, SENT, FAILED, CANCELLED; lastError содержит только безопасный код.
  Для диагностики проверять рост PENDING/FAILED и доступность webhook, в том числе подписку MAX.

Ограничение внешних API: если бот принял исходящее сообщение, а ответ API потерялся, повтор может
создать вторую копию в мессенджере. Сайт при этом сохраняет одно Message. Exactly-once для внешней
доставки не заявляется. Доставка не считается прочтением чата.

## Проверки

```sh
# PostgreSQL, изолированные тестовые пользователи удаляются после тестов:
MESSENGER_DB_TESTS=1 npx vitest run src/messengers src/chat
# Из frontend:
npx vitest run widgets/messenger-settings app/api/messengers widgets/customer-requests/model/conversation-selection.test.ts
```

Проверены на локальном PostgreSQL: подтверждение владельцем, уникальность привязки, истечение ссылки,
одна доставка при конкуренции worker, идемпотентность ответов Telegram/MAX, чужие уведомления,
отзыв membership, отмена очереди при отключении, повтор после 429. Внешний транспорт в тестах заменён.
Снимки UI: `artifacts/messengers/2026-11-04/`; `mobile-confirmation-fixture.png` использует тестовый
ответ API для показа подтверждения, а не реально подключённые боты.

Результат: 46 backend-тестов (включая 20 существующих тестов чата) прошли после перехода на события.
Проверены отсутствие опроса пустой очереди в течение виртуального часа, запуск по NOTIFY,
повтор точно в назначенное время, сигналы во время отправки и переподключение слушателя.
На реальном PostgreSQL проверены уведомление после COMMIT, отсутствие его при ROLLBACK,
восстановление после отключения слушателя и порядок отложенных заданий.
13 frontend-тестов прошли при реализации интерфейса; в изменении планировщика frontend не менялся.
Пройдены Prisma validate, ESLint нового модуля/интерфейса и сборка backend.
В браузере проверены реальные авторизованные BFF-запросы (200), клиентский профиль и настройки
исполнителя на ширине 390 px, отсутствие горизонтальной прокрутки. Заодно исправлено переполнение
профиля длинным email на мобильном экране.

Полные проверки TypeScript обоих пакетов имеют существующие ошибки в старых тестовых файлах.
Сборка backend и отдельная проверка рабочего кода frontend выполняются независимо от них.

После заполнения токенов обязательно проверить на настоящих аккаунтах: обе привязки, сайт → Telegram,
сайт → MAX, ответ из каждого бота → сайт, переписка Telegram ↔ MAX, две заявки одновременно,
отключение бота и ответ в архивный чат. До этого реальные боты не считать введёнными в эксплуатацию.
