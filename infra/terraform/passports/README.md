Отдельный Terraform root для **одного** S3-совместимого бакета в российском регионе Yandex Cloud. Он не изменяет основную инфраструктуру `infra/terraform` или testing. Статус: инфраструктура создана и проверена 2026-11-06; локальный backend подключён для файлов документов и JSON-анкет, развёртывание на сервере и перенос старых файлов ещё не выполнены.

- Folder: `b1gcdvf6jupvtiqplmo6`.
- Бакет: `zemledel-prod-plmo6-passports`.
- KMS-ключ: `abjtimnbvhsb11k0mm46`.
- Сервисный аккаунт backend: `ajedl0f97h76t5hg9ckt`.

Проверка 2026-11-06: каталог `prod` имеет статус `ACTIVE` и принадлежит указанному облаку. Apply выполнен; повторный plan завершился с **No changes**. В state шесть ресурсов: бакет, KMS-ключ, аккаунт backend, разрешение на ключ, ACL с именованными получателями и отдельная политика бакета.

Проверено от имени backend на короткоживущем IAM-токене: загрузка и чтение синтетического JSON с ожидаемым SSE-KMS-ключом, отказ без SSE-заголовков и с неверным ключом, отказ записи вне `passports/`, приостановка версионирования, перезапись без сохранения предыдущего содержимого, удаление текущего объекта и окончательное удаление null delete marker. Анонимные HTTPS/HTTP-чтение и листинг отклонены. Авторизованный HTTP не проверялся: bearer-токен по незащищённому каналу не передавался; запрет закреплён политикой. Все тестовые объекты, версии и markers удалены.

Повторить проверку (создаёт только синтетические объекты с уникальным префиксом и удаляет их в `finally`):

```sh
python3 infra/terraform/passports/scripts/smoke-test.py
```

Анкета и фотографии разделены объектами, а пользовательские разрешения — записями в backend:

```text
passports/<opaque-user-id>/form/<random-object-id>.json
passports/<opaque-user-id>/photos/<random-object-id>.jpg
```

В ключах объектов, метаданных и логах не должно быть ФИО, серии/номера паспорта, адреса или исходного имени файла. JSON остаётся JSON-объектом, фотография — изображением: прозрачное серверное шифрование не меняет формат при авторизованном чтении.

## Что настроено

Аудит и эксплуатационный мониторинг подготовлены отдельными конфигурациями
`audit.tf` и `monitoring.tf`. Созданы аккаунт, ключ, бакет и трейл аудита;
создание панели завершилось ошибкой провайдера, а доставку событий ещё нужно проверить.
Подробный статус, ресурсы и проверки: [эксплуатация документов](../../../docs/private-document-operations.md).

- Один приватный бакет; анонимные чтение, листинг и чтение конфигурации отключены. Нет CDN, сайта и CORS.
- KMS AES-256, автоматическая ротация каждые 90 дней, защита ключа от удаления. Ротация не перешифровывает старые объекты: старые версии ключа нельзя удалять, пока они нужны данным.
- SSE-KMS по умолчанию; политика также отклоняет `PutObject` без `aws:kms` и ID выбранного ключа. Будущий backend должен передавать оба заголовка явно.
- Запрет HTTP для всех S3-операций.
- Отдельный сервисный аккаунт backend. Права только на объекты `passports/*` и `documents/*`, листинг этих префиксов и использование одного KMS-ключа. Базовые права на данные выданы именованной ACL `READ` + `WRITE`; политика сужает их до `passports/*` и `documents/*`. Нет `FULL_CONTROL` для backend, назначения ролей Object Storage на каталог или облако и прав администрирования KMS.
- Версионирование приостановлено (`Suspended`, `versioning.enabled = false`): новые записи используют версию `null`, перезапись не сохраняет предыдущее содержимое. Ранее включённый бакет нельзя вернуть в состояние без версионирования. Обычный DELETE по-прежнему оставляет delete marker; backend должен удалять его явно. Правила очистки исторических версий через 7 дней и пустых markers оставлены как страховка; новые исторические версии не создаются. Незавершённые multipart-загрузки очищаются через день.
- `prevent_destroy` для бакета, ключа и сервисного аккаунта; `force_destroy = false`. Эти ограничения не заменяют контроль прав в облаке.

Политика явно разрешает управление существующему аккаунту Terraform (`terraform_service_account_id`). Права IAM и ACL проверяются совместно с политикой: одного IAM-доступа недостаточно для операций, отсутствующих среди её разрешений. При смене аккаунта Terraform сначала добавьте новый доверенный аккаунт в политику, чтобы не потерять возможность управления. Исполнители не получают сервисный аккаунт, S3-ключи или KMS-доступ: проверки конкретной заявки, вида документа, срока и отзыва выполняет backend.

## Подготовка и проверка

Нужны существующие cloud/folder в российском облаке и отдельная учётная запись для Terraform. Для создания ресурсов ей нужны права управления Object Storage, сервисными аккаунтами и KMS, включая назначение прав на ключ. Не используйте runtime-аккаунт приложения для Terraform.

Локально настроен отдельный CLI-профиль `passport-terraform`; прежний активный профиль не изменён. Авторизованный ключ хранится вне репозитория с правами `0600`:

```sh
export YC_SERVICE_ACCOUNT_KEY_FILE="/Users/pavelusov/.config/yandex-cloud/passports-terraform-key.json"
```

Terraform читает `YC_TOKEN` или `YC_SERVICE_ACCOUNT_KEY_FILE` из окружения. Секреты не передаются через `.tfvars`. Настройка аутентификации: [официальная инструкция](https://yandex.cloud/ru/docs/terraform/authentication).

```sh
umask 077
cp -n infra/terraform/passports/terraform.tfvars.example infra/terraform/passports/terraform.tfvars
# Проверить cloud_id, folder_id, name_prefix и terraform_service_account_id.
terraform -chdir=infra/terraform/passports init
terraform -chdir=infra/terraform/passports fmt -check
terraform -chdir=infra/terraform/passports validate
terraform -chdir=infra/terraform/passports plan -out=passport.tfplan
```

На текущем окружении plan должен показывать отсутствие изменений. Для нового окружения ожидаются шесть ресурсов: один бакет, один ключ, один сервисный аккаунт, разрешение на ключ, ACL и политика. Проверить отсутствие незапланированных удалений перед apply. Затем при готовности выполнить `terraform -chdir=infra/terraform/passports apply passport.tfplan`. Идентификаторы подключения: `terraform -chdir=infra/terraform/passports output -json passport_storage` — этот output не содержит секретов.

Root пока использует локальный state. До командной/CI-эксплуатации перенести state в отдельное защищённое хранилище с блокировкой, своим жизненным циклом и ограниченным IAM. Не размещать state в бакете паспортов. `.tfstate`, `.tfvars` и планы игнорируются Git; `.terraform.lock.hcl` следует коммитить.

Долгоживущие ключи backend Terraform намеренно не генерирует: секрет статического S3-ключа иначе попадёт в state. Метод авторизации приложения выбирается по его окружению. При необходимости статического ключа создать его отдельно, сохранить в менеджере секретов и выдавать только runtime; не подменять общие `S3_*` переменные приложения этими реквизитами.

## Следующий этап в приложении

Публичные изображения остаются на `S3Service`. Все новые документы заявок используют отдельный `DocumentStorageService` и префикс `documents/`; исторические ключи читаются из прежнего хранилища до миграции. Новые паспортные анкеты сохраняются в S3 как JSON с KMS; старые зашифрованные записи БД переходят в S3 при следующем сохранении. Этот root ничего не переносит и не меняет UI-заявление о соответствии 152-ФЗ.

Для подключения нужно:

1. Отдельный клиент хранилища паспортов, использующий output выше. Для `PutObject` обязательны `ServerSideEncryption: "aws:kms"` и `SSEKMSKeyId`. Для паспорта достаточно одиночного PUT до 10 МБ; multipart/copy требуют отдельной проверки совместимости с политикой.
2. Хранить в БД только ссылки и необходимые служебные поля, отдельно от JSON и фото. Перенос существующих анкет выполнять отдельной миграцией с проверкой чтения и удалением прежних копий по принятому сроку хранения.
3. Раздельные разрешения `form` / `photo` для конкретного исполнителя и заявки реализованы в приложении: срок, отзыв и аудит чтения/изменения разрешений. Прежний автоматический доступ по статусу заявки удалён. Для немедленного отзыва отдавать файл через backend с `Cache-Control: no-store`; ранее выданная подписанная ссылка действует до истечения срока, а скачанную копию отозвать нельзя.
4. При удалении паспорта отзывать доступ и удалять **все версии объектов и delete markers**, а не только создавать новую отметку удаления. Это относится и к версии `null` / delete marker после приостановки версионирования. Фоновая очистка не заменяет явное удаление по запросу. Согласовать сроки текущих данных, резервных копий и аудита.
5. Подключить аудит операций хранилища/KMS и мониторинг; проверить восстановление. Дополнительное прикладное envelope-шифрование (AES-GCM, отдельный DEK на объект, обёрнутый отдельным KMS-ключом) — отдельная backend-задача, не реализованная этой конфигурацией. SSE-KMS уже шифрует данные на стороне хранилища.

При будущих изменениях политик повторять smoke-test выше. Ответ ListObjectVersions может содержать корень XML с namespace и дочерние Version/DeleteMarker без namespace: обработка удаления должна учитывать обе формы и подтверждать непустой список версий до очистки. `terraform validate` проверяет схему конфигурации, но не заменяет реальные проверки в облаке.

Выбор облака и SSE-KMS сами по себе не подтверждают соответствие всей системы 152-ФЗ. Нужны проверка применимости документов провайдера к выбранным сервисам и выполнение обязанностей оператора для приложения, доступов, обработки и удаления данных.
