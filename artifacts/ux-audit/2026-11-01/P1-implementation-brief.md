# Задание для Cursor Composer: исправить P1 в workflow заявок

Контекст: [UX-отчёт](report.md) и скриншоты в этом каталоге. Реализация в Cursor Composer; итоговую проверку интерфейса под клиентом и исполнителями проведём отдельно через Chrome DevTools. Работать в существующей архитектуре Next.js + NestJS, сохраняя изменения небольшими и проверяемыми.

Проект находится в разработке. Совместимость со старыми финансовыми записями, перенос прежних платежей и backfill не входят в задачу. Проверять новое поведение на новых тестовых заявках. Правила доступа и расчёта для новых заявок остаются обязательными.

## Сверка продуктовых правил до реализации

В `docs/business-logic.md` есть правила, которые расходятся с предлагаемыми ниже изменениями. Это **продуктовые решения**, а не мелкие технические детали. Перед написанием кода подготовить короткую таблицу «текущее правило → наблюдаемый UX-дефект → рекомендуемое новое правило → затронутые сценарии» и вынести спорные решения пользователю. После выбора обновить `docs/business-logic.md` одновременно с реализацией, чтобы документация и код описывали одно поведение.

- **Цена:** документ сейчас разрешает каждой стороне менять `totalAmountRubles` без подтверждения другой, не требует суммы для акцепта договора и определяет `servicePriceRubles` как снимок цены карточки без статуса согласования. Требование ниже о **согласованной** цене до подписания меняет эти правила. Нужно определить, является ли цена карточки фиксированной ценой сделки или ориентиром, кто предлагает сумму, как вторая сторона подтверждает её и что происходит при изменении уже после подписания. Не выдавать действующий односторонний ввод суммы за взаимное согласование.
- **Поздняя оплата:** документ прямо запрещает любые записи после `COMPLETED`, тогда как требование ниже предполагает учёт позднего поступления. Нужно решить, допускается ли отдельный финансовый журнал после завершения работ, кто вправе в нём писать и можно ли добавлять новые платежи или только подтверждать ранее запланированные.
- **Завершение с остатком:** раздел жизненного цикла документа говорит о завершении при остатке ≤ 0, если цена задана; раздел оплаты говорит, что цена переход «Завершить» не блокирует. Проверенный интерфейс позволил завершить FREEFORM с остатком. Нужна единая формулировка правила в документации, API и интерфейсе.

`brainstorming` здесь полезен именно для этой короткой сверки. Не расширять задачу до нового дизайна всего продукта: итогом должны быть конкретные решения по трём расхождениям и исполнимый план четырёх P1.

## Два сценария, которые должны остаться разными

1. **SERVICE:** клиент создаёт заявку из карточки услуги. Исполнитель заранее известен; выбора среди компаний нет. Согласование договора → работа → сдача → приёмка → завершение.
2. **FREEFORM:** клиент создаёт свободную заявку через «Нужна помощь?». Несколько исполнителей могут откликнуться, у каждого свой чат. Клиент выбирает одного исполнителя после общения. Только после выбора договор и дальнейший цикл.

Не превращать SERVICE в сценарий выбора исполнителя. Не смешивать переписки разных исполнителей FREEFORM.

## P1. Выбор исполнителя должен переключать чат

**Воспроизведение:** в FREEFORM открыть чат компании А, выбрать компанию Б. Сейчас подтверждение выбора Б появляется, но остаётся чат А с активным вводом; отправка заканчивается `Forbidden`.

**Требуемое поведение:**

- После успешного ответа на `select-provider` открыть чат выбранной компании Б. При ошибке выбора сохранить прежнее состояние и показать понятную причину.
- Чаты остальных компаний оставить доступными для чтения. В них показать, что выбран другой исполнитель, убрать возможность отправлять сообщения и кнопку повтора отправки.
- После обновления страницы или открытия заявки снова должен открываться чат выбранного исполнителя либо список с явно выделенным выбранным чатом. Если чат ещё загружается, не оставлять активным ввод в чате другой компании.
- Если сервер отклонил сообщение из-за смены статуса, заменить техническое `Forbidden`/`Request is locked` понятным русским состоянием и действием перехода к выбранному чату. Серверное ограничение доступа сохранить.

**Готово, когда:** выбор Б из чата А сразу открывает Б; сообщение Б отправляется; А виден только для чтения; обновление вкладки не возвращает активный ввод А. SERVICE по-прежнему не показывает список выбора.

Ориентир в коде: `frontend/widgets/customer-requests/ui/CustomerRequestConversationWorkspace.tsx`, `selectProvider` и `selectedConversationId`; правила доступа к чату проверить и на сервере.

## P1. При сдаче клиент должен видеть предъявленный результат

**Воспроизведение:** исполнитель нажимает «Услуга выполнена» без этапов, описания и файлов; у клиента начинается семидневный срок приёмки, но непонятно, что проверять.

**Требуемое поведение:**

- Перед переводом в «Ожидает принятия» запросить у исполнителя обязательный краткий итог: что сделано и как клиент получил или может получить результат. Ссылки и файлы разрешить при наличии; обязательную загрузку файла для консультаций не вводить.
- Сохранять итог на сервере вместе с фактом сдачи; валидация должна работать и при прямом запросе к API. Показывать этот итог клиенту рядом с действиями «Принять результат» и «Отправить замечания», с датой сдачи.
- При повторной сдаче после замечаний запросить, что именно исправлено. Сохранить историю предыдущей сдачи и замечаний, чтобы было понятно, какая версия принималась. Если в текущей модели уже есть пригодный механизм истории, использовать его.
- Не запускать срок автоматического принятия до успешного сохранения итога. Существующие заявки без итога должны открываться без ошибок; не придумывать для них текст результата.

**Готово, когда:** пустой итог нельзя сдать ни через UI, ни через API; сданный итог виден клиенту до приёмки; после замечаний и повторной сдачи виден новый итог; семидневный срок начинается после успешной сдачи.

Ориентир: действие `markRendered` в `frontend/widgets/pro-requests/ui/ProRequestDetails.tsx`; серверный переход статуса и модель заявки найти перед изменением схемы.

## P1. Завершение работ не должно закрывать учёт поздней оплаты

**Воспроизведение:** FREEFORM завершена с остатком 12 000 ₽. Предупреждение честно сообщает, что после завершения отмечать оплаты нельзя. Поздний платёж уже невозможно учесть в интерфейсе.

**Требуемое поведение:**

- Разделить состояние выполнения работ и состояние расчётов. Статус `COMPLETED` означает, что работы завершены; оставшийся платёж может быть отмечен позднее. Новые оплаты после завершения работ также должны быть доступны, если это нужно текущей модели финансовых записей.
- В завершённой заявке показывать согласованную цену, оплачено и остаток. Отметка поступления должна менять сумму остатка, сохраняя дату, сумму и автора записи. Повторное подтверждение одной оплаты должно быть защищено.
- Убрать из диалога завершения утверждение, что отметки оплат станут недоступны. Если остаток есть, показать сумму и сообщить, что оплата может быть отмечена позже.
- Не открывать финансовые действия для посторонних исполнителей или отменённых заявок; проверить правила доступа и на клиенте, и в API. Не отмечать оплату автоматически при завершении.

**Готово, когда:** завершённая заявка с остатком сохраняет действие учёта оплаты; после отметки остаток пересчитывается у клиента и исполнителя, статус работ остаётся завершённым; второй исполнитель не получает доступ к чужим расчётам.

Ориентир: `frontend/widgets/request-payments/ui/RequestPayments.tsx` (`CLOSED`, `canMarkPaid`), `backend/src/request-payments/request-payments.service.ts` (`CLOSED_STATUSES`) и диалог завершения в `ProRequestDetails.tsx`. Изменить обе стороны правила, а не только видимость кнопки.

## P1. Цена SERVICE при подписании должна совпадать с финансовым учётом

**Воспроизведение:** при подписании SERVICE показано 12 000 ₽, но после завершения в финансах цена работ пуста, остаток «—». `servicePriceRubles` и `totalAmountRubles` передаются отдельно; остаток вычисляется из `totalAmountRubles`.

**Требуемое поведение:**

- До подписания договора у заявки должна быть одна явно согласованная **цена работ**. Для услуги с фиксированной ценой допустимо предложить цену карточки как исходное значение. Если цена карточки ориентировочная («от…»), нужно явное согласование окончательной суммы. Не извлекать сумму из сообщений чата автоматически.
- При подписании показывать именно согласованную цену работ; ту же сумму использовать в панели оплаты, при приёмке и завершении. Для 12 000 ₽ без оплат остаток равен 12 000 ₽.
- Если цена ещё не согласована, показывать «Цена не согласована» и не подменять её ценой карточки в подтверждении договора. Нужный шаг согласования реализовать в обеих ролях до подписания.
- При смене исполнителя FREEFORM прежняя цена не должна молча переходить к новой компании: требуется новое явное согласование. Предложение в чате само по себе не фиксирует цену.
- Для новой заявки без согласованной суммы показывать «Цена не согласована»; не подставлять цену карточки как подтверждённую цену работ.

**Готово, когда:** новая SERVICE с согласованной ценой 12 000 ₽ показывает 12 000 ₽ при подписании и в финансах; без оплат остаток 12 000 ₽. При смене исполнителя FREEFORM прежняя сумма требует нового подтверждения.

Ориентир: `backend/src/requests/dto/request.dto.ts` (`toFinanceDto`), `backend/src/request-payments/request-payments.service.ts`, цена в диалоге подписания и `RequestPayments.tsx`.

## Порядок работы и проверка

1. Сначала изучить текущие модели заявки, API, переходы статусов и тесты. Кратко отметить в ответе, где хранится согласованная цена, кто может её менять и как фиксируется факт сдачи. При расхождении с этим документом сохранить продуктовые требования и адаптировать реализацию к архитектуре.
2. Реализовывать небольшими этапами: **цена → оплаты после завершения → переключение чата → предъявление результата**. После каждого этапа проверить соответствующий серверный переход и UI; не откладывать всю проверку на конец.
3. Добавить содержательные автоматические проверки прав доступа и расчётов, переходов с пустым/повторным итогом, выбора исполнителя при открытом чужом чате. Не ограничиваться тестами, повторяющими условия компонентов.
4. Запустить подходящие проверки в `backend` (`npm test`, `npm run lint:check`, `npm run build`) и `frontend` (`npm test`, `npm run lint`, `npm run build`). Если весь набор занимает слишком много времени, выполнить минимум релевантные тесты и сборки, явно указав пропущенное.
5. В результате перечислить изменённые файлы, миграции и поведение каждой из четырёх правок; сообщить оставшиеся риски. Не создавать реальные оплаты, не отправлять внешние уведомления и не менять дизайн вне затронутых экранов.

После реализации пользователь запускает приложение на `http://localhost:4000`; браузерную проверку в этом Codex-чате проведём на **новых тестовых заявках** под клиентом и двумя исполнителями.
