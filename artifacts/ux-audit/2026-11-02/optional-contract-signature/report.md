# Необязательный готовый файл подписи договора

Дата: 02.11.2026. Решение пользователя: договор обязателен, прикрепление готовой подписи опционально. Будущая возможность «Подписать КЭП» записана в [отдельный план](../../../../plans/2026-11-02-contract-kep-signing.md).

## Реализация

- Multipart API требует только `document`; `signature` передаётся и сохраняется, только если файл действительно приложен. Swagger отражает необязательность подписи.
- Сам договор остаётся обязательным. Приложенная подпись по-прежнему должна иметь поддерживаемое расширение `.sig`, `.sgn` или `.p7s` и непустое содержимое.
- При ошибке записи удаляются только уже загруженные объекты хранилища. Ошибка загрузки подписи также очищает ранее загруженный договор.
- У клиента отсутствие подписи больше не блокирует одобрение документа и акцепт договора. На сервере сохраняются требования к выбранному исполнителю, согласованной цене, наличию и одобрению всех договоров и загрузке запрошенных документов.
- В форме: «Договор · обязательно», «Файл подписи · необязательно», «Прикрепить файл подписи». Пояснение явно говорит о загрузке уже созданного файла. Добавлено действие «Убрать файл подписи».
- В карточке отсутствие подписи обозначается нейтрально: «Файл подписи не приложен». Криптографическая проверка и создание КЭП не реализованы и не заявляются.
- Схема БД не менялась: отдельная строка `CONTRACT_SIGNATURE` и ранее могла отсутствовать, DTO уже допускает `signature: null`.
- Актуализирован `docs/business-logic.md`; исторические планы и отчёты прошлых проверок сохраняют описание прежнего поведения.

## Скачивание: исправлено после отдельной проверки

Первоначально скачивание возвращало `500` и у клиента, и у исполнителя. Причина: исходное имя с кириллицей напрямую подставлялось в `Content-Disposition`; Node отклоняет такой заголовок с `ERR_INVALID_CHAR`.

Во всех восьми download-обработчиках договоров, запрошенных документов и файлов этапов заголовок теперь формируется библиотекой `content-disposition`: поддерживаются UTF-8 `filename*`, безопасный fallback и экранирование специальных символов. Права доступа и потоковая передача не менялись.

Повторная проверка в Chrome DevTools MCP:

- SERVICE `95015bc0…`: PDF скачивается у клиента и исполнителя с `200`; у клиента также проверен `inline=1` — `200`, `inline`, `application/pdf`.
- FREEFORM `e1d212d2…`: PDF и `.sig` скачиваются у клиента и выбранного исполнителя с `200`.
- Завершённая SERVICE `3aa17bef…`: ранее загруженные PDF и `.sig` скачиваются у исполнителя с `200`.
- SHA-256 полученных PDF и подписей совпадает с оригинальными тестовыми файлами: PDF `ca50439cced82b73cc83c4905206db3865a32a4f9ef8c88b8a231d41b660062f`, подпись `be13c8bb8172eab2341f9c8abe7db90c41aa4abe89dc12cbb53efb56c5be3ec3`.
- Второй исполнитель при обращении к файлу чужой SERVICE получает `404`.
- В интерфейсе исполнителя раскрыты документы и нажата ссылка «Скачать договор».

Добавлен `contract-files.download.spec.ts`: 10 HTTP-тестов с настоящим Node HTTP-ответом для обеих ролей — кириллица, подпись, inline, кавычки и CRLF в имени. Вместе с проверками необязательной подписи и акцепта **31/31**. Backend build успешен, lint — 0 ошибок и 311 предупреждений. Отдельная браузерная регрессия файлов этапов и запрошенных документов не проводилась.
