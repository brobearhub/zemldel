# Полные тесты, гостевой путь и мобильная проверка

Дата: 02.11.2026. Ветка `dev`. Основные исправления договора, скачивания и архивных чатов зафиксированы коммитом `5d06710` (`fix: сделать подпись договора необязательной и исправить UX чатов`). Проверка выполнялась на локальном приложении через Chrome DevTools MCP в трёх существующих изолированных сессиях клиента и двух исполнителей.

## Полные тесты

| Пакет | До исправления тестов | После |
|---|---|---|
| Backend | 360 passed / 2 failed, 71 файл | **362/362, 71/71 файлов** |
| Frontend | 545 passed / 22 failed, 127 файлов | **567/567, 127/127 файлов** |

Команды: `npm test -- --reporter=dot` в каждом пакете. Финальные полные прогоны: backend 19.70 с, frontend 45.85 с. Окружение: Node `v26.12.1`, Vitest `3.2.4`. Снижение количества тестов, отключение падений и увеличение таймаутов не применялись.

Причины и изменения:

1. **Frontend, 21 тест:** Node 26 предоставляет глобальный `localStorage`, недоступный без соответствующей настройки. Vitest 3 сохранял этот Node-global вместо браузерного storage; в тестах `window.localStorage` оказывался `undefined`. В `vitest.setup.ts` глобальные `localStorage`/`sessionStorage` привязаны к настоящим Storage текущего jsdom-окружения. Изменение действует только в тестах, фиктивная заглушка Storage не добавлялась.
2. **Frontend, 1 тест:** фикстура ожидала кнопку заключения договора, но не содержала согласованной цены. Добавлена цена 12000, как в актуальном положительном сценарии модели. Продуктовое требование к цене сохранено.
3. **Backend, 1 тест:** шаблонное ожидание `Hello World!` заменено на действующий ответ `ZemledelPro API`.
4. **Backend, 1 тест:** in-memory транзакция сценария двух сдач не реализовывала `$queryRaw`, используемый после добавления блокировки строки. Mock теперь возвращает строку текущего транзакционного состояния для соответствующего ID. Реальная блокировка PostgreSQL не подменялась в коде приложения.

Перед общими прогонами профильные проверки прошли: frontend 25/25, backend 3/3. Бизнес-логика приложения в этом этапе не менялась. Ранее отмеченный случайный таймаут админского теста в текущем полном прогоне не повторился.

## Гость → SERVICE → вход → заявка

Новая запись: **`3e04e38f-4310-49ad-8878-266483627969`**, исполнитель ООО «Бурый Медведь».

1. В клиентской сессии выполнен выход через меню, открыта главная страница как гость. На ширине 360 px видны два различающихся пути в hero. [Главная](01-guest-home-360.jpg).
2. Через карточку услуги открыт её экран. В гостевой форме введены тестовый вопрос, участок `66:41:0000000:123` и email существующего тестового клиента. [Заполненная форма](02-guest-service-draft.jpg).
3. «Продолжить» открыло регистрацию клиента с сохранёнными вопросом и участком. [Сохранённая SERVICE](03-service-draft-at-signup.jpg).
4. По ссылке «Войти и продолжить» открыт вход с тем же контекстом. После входа создана SERVICE и автоматически открыта её карточка с сообщением об отправке исполнителю. [Результат входа](04-service-created-after-signin.jpg).
5. API подтвердил тип SERVICE, ожидаемого исполнителя, исходный вопрос и кадастровый номер. Чат содержит вопрос. Под исполнителем эта заявка также доступна с исходным текстом.
6. В списке клиента ровно одна заявка с этим тестовым маркером. Повторный переход на callback `requestResume=1` дубль не создал; после удаления использованного черновика интерфейс объясняет, что черновик в этой вкладке не найден.

## Гость → FREEFORM → редактирование → вход → два отклика

Новая запись: **`e4fd4ef9-2c35-47de-a49d-fd3752d41dfe`**, позднее выбран ИП Медведев.

1. После выхода клиента на главной открыта «Своя заявка». В модальной форме заполнены задача, Екатеринбург и участок `66:41:0000000:456`. [Форма](05b-guest-freeform-filled.jpg).
2. «Продолжить» открыло регистрацию со всеми тремя данными и объяснением, что заявку увидят подходящие исполнители. [Сохранённая FREEFORM](06-freeform-draft-at-signup.jpg).
3. По ссылке «Изменить заявку» снова открылась форма с сохранённой задачей; после повторного продолжения экран входа содержал прежние задачу, город и участок.
4. После входа автоматически открыта опубликованная заявка. GET карточки подтвердил FREEFORM, `providerId=null`, Екатеринбург и исходный участок. Ровно одна запись с тестовым маркером. [Пустое состояние после публикации](07-freeform-created-after-signin.jpg).
5. Оба исполнителя открыли заявку на ширине 360 px и отправили тестовые сообщения через UI чата. У клиента появились два отдельных отклика. На 320 px имена и кнопки не перекрывались, горизонтального переполнения нет. [Два отклика](08-freeform-two-offers-320.jpg).
6. Клиент выбрал ИП через подтверждение. Открытый экран ООО автоматически стал архивным: ввод отключён, «Ответить» отсутствует, финансы и рабочие действия скрыты. [Мобильный архив ООО](09-mobile-archived-provider.jpg).

Подготовка обоих гостевых черновиков, переходы регистрации/входа, авторизация, публикация, сообщения исполнителей и выбор выполнены интерфейсом. Авторизованные API-чтения использованы только для контрольных ID, данных и количества записей. Свежая регистрация нового пользователя и доставка писем в этой проверке не выполнялись: вход использовал предоставленный тестовый аккаунт.
