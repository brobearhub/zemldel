# Потеря ответа после записи: локальная проверка

Дата: 02.11.2026. Ветка `dev`, localhost:4000 / backend:4003, реальный PostgreSQL. Проверка через Chrome DevTools MCP в трёх существующих изолированных вкладках: клиент, выбранный исполнитель, другой исполнитель. Это проверка локальных изменений, не тестового стенда ONREZA.

## Подтверждённая проблема

До исправления FREEFORM-заявка успешно создавалась на сервере, но потеря ответа оставляла форму открытой. Повтор создавал вторую заявку: `ed78f028-f9c5-46cb-b4dc-9205d197325b` и `bd0bdfa9-a50d-44ab-a7c8-94749a68e6db`.

Доказательства: [созданный дубль](01-freeform-duplicate-created.jpg), [две заявки в списке](02-freeform-duplicates-in-list.jpg).

## Что изменено

- Новый `operationId` сохраняется в sessionStorage до подтверждения записи. Повтор того же действия использует прежний ключ; изменённые данные означают новое действие. GET-запросы не создают и не сбрасывают ключи.
- PostgreSQL хранит результат операции в `WriteOperation` в одной транзакции с предметной записью. Advisory lock сериализует одинаковые операции между процессами. Совпавший ключ с другим содержимым возвращает 409. Проверка текущих прав выполняется до возврата результата повторной операции.
- Защищены создание SERVICE/FREEFORM/категорийной заявки, создание платежной записи, загрузка пакета договора и запрошенного клиентского документа. Повтор отметки оплаты не создаёт второе событие.
- SERVICE сохраняет намерение создания до открытия чата и подтверждения первого сообщения; ID первого сообщения стабилен и равен ID заявки.
- Исходящие сообщения сохраняют `clientMessageId` при потере ответа, перезагрузке и повторном входе. История сообщений удаляет из очереди уже доставленные сообщения. Повтор ID с другим текстом отклоняется сервером.
- Замена клиентского документа использует новый ключ объекта: неудачная запись БД не повреждает предыдущий файл. После потери ответа клиент сверяет имя и SHA-256 с сервером и подтверждает фактически состоявшуюся загрузку.

## Браузерные проверки

Потеря ответа моделировалась после завершения настоящего успешного HTTP-запроса: тестовая обёртка `fetch` выбрасывала ошибку вместо передачи ответа интерфейсу. Для проверки повторной доставки сообщения дополнительно временно блокировался WebSocket, чтобы событие не заменяло потерянное HTTP-подтверждение. После проверки обычное соединение восстановлено.

Ошибка `QA request did not reach server` / `QA lost …` на некоторых скриншотах — текст искусственно внедрённого сбоя, а не ответ приложения. Для потери сессии использован штатный signout endpoint без навигации; естественное истечение JWT не ожидалось.

Во время реализации обнаружена и исправлена промежуточная регрессия: GET списка попадал в обёртку записи, перезаписывал ключ незавершённой загрузки и приводил к дублю договора. Оба созданных в этом промежуточном прогоне пакета удалены; финальный повтор с чтением между POST прошёл. `10-contract-response-lost-file-kept.jpg` относится к промежуточному прогону и не является доказательством успешного финального сценария. Добавлен отдельный тест, запрещающий GET изменять намерение записи.

## Границы результата

- Две добавочные миграции применены к локальной БД; на ONREZA их и код ещё нужно развернуть и повторить сценарии.
- Старые клиенты без `operationId` продолжают работать; гарантия безопасного повтора новых создающих операций требует стабильного ключа. Браузер проверял авторизованные формы SERVICE и FREEFORM; гостевой переход через регистрацию и категорийная форма в этом прогоне отдельно не проходились.
- sessionStorage действует в пределах вкладки. Между независимыми вкладками новые действия получают разные ключи; два намеренно разных действия не объединяются.
- Покрыты основные договорные документы и запрошенные клиентские документы. Прочие вложения этапов/дополнительные материалы не объявляются проверенными этим пунктом.
- Полный жизненный цикл до COMPLETED здесь повторно не проходился: проверялись сбои записи и восстановления. Автоприёмка и доступность форм остаются следующими отдельными пунктами плана.
- Изменения не закоммичены и не опубликованы.
